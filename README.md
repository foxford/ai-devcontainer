# ADC: рабочая среда для AI-разработки

ADC помогает работать с AI-агентами в нескольких проектах. Вы подключаете свои репозитории, а агенты получают общие знания команды, карту проектов и инструкции для работы с каждым из них: как проверять код, готовить релизы и пользоваться нужными инструментами.

Все проекты доступны в одной изолированной среде. Через Orca можно запускать агентов параллельно, создавать отдельные рабочие ветки с помощью Git worktree и управлять задачами и терминалами.

## Что это даёт

- Общие инструкции и скиллы обновляются из одного места для всех подключённых проектов.
- Агент видит, какие проекты связаны, и может учитывать код и документацию соседнего репозитория при решении задачи.
- Для каждого проекта можно выбрать свои возможности: Changesets, браузерные инструменты, Figma и другие.
- Инструменты и агенты работают внутри Docker. Вы подключаете существующие репозитории со своим стеком и конфигурацией.

## Начать работу

Если вы уже используете прежний ADC в проектных devcontainer, начните с [перехода на новую среду](docs/migration.md). Новый adc заменяет прежнюю команду; данные копируются в новые тома, оригиналы сохраняются для восстановления.

Установите ADC и Orca одной командой для своей ОС.

macOS / Linux:

```sh
curl -fsSL https://raw.githubusercontent.com/foxford/ai-devcontainer/main/install.sh | sh
```

Windows (PowerShell):

```powershell
irm https://raw.githubusercontent.com/foxford/ai-devcontainer/main/install.ps1 | iex
```

Откройте новый терминал: команда `adc` и автодополнение уже подключены. Подробности и поддерживаемые ОС описаны в [инструкции по установке](docs/installation.md).

Подключите проекты и запустите среду. Пути в примере замените на свои:

```sh
adc project add ~/Development/frontend --id frontend --capability pnpm-nx,changesets,frontend
adc project add ~/Development/backend --id backend --description 'API продукта'
adc project relate frontend backend
adc workspace start
```

Откройте Orca на компьютере и [подключите её к ADC](#настроить-orca). В Orca появятся подключённые проекты; можно создавать worktree, открывать терминалы и запускать агентов. Логины и подписки агентов подключите внутри среды. Для обновления выполните на хосте `adc update`: работающий workspace перезапустится автоматически. Перед обновлением завершите задачи агентов. Если переключение прервалось, продолжите через `adc workspace start`; порядок восстановления описан в [инструкции по обновлению](docs/installation.md#обновление-и-диагностика).

В среде установлены Claude Code, Codex, OpenCode, Hermes и DSH. Выберите нужного агента в Orca или запустите его CLI в терминале проекта.

## Настроить Orca

Приложение Orca показывает проекты, файлы и сессии агентов, которые работают на сервере внутри ADC. Один сервер содержит все подключённые проекты. В примерах ниже workspace называется `developer`, контейнер — `adc-developer`.

### Подключить сервер

После `adc workspace start` выполните на хосте, где установлен ADC; при установке в WSL — в терминале WSL:

```sh
adc workspace status
adc orca status --json
adc orca repo list --json
adc workspace logs
```

Ожидайте `running (готов)`, `runtime.reachable: true` и свои проекты в списке `repos`. В логах найдите событие `orca_server_ready` и скопируйте целиком значение `pairing.url`, начинающееся с `orca://pair?code=`. Если событие уже вышло за пределы последних строк, посмотрите полные логи: `docker logs adc-developer`. Pairing URL предоставляет доступ к среде; не сохраняйте его в Git и не публикуйте в скриншотах.

1. В приложении Orca нажмите **⚙️ → Remote Orca Servers → Add Server**.
2. В **Name in Orca** введите `ADC Developer`, в **Access link** вставьте pairing URL.
3. Для ADC на этом же компьютере адрес назначения обычно `127.0.0.1:6768`. Если Orca показывает **This link points back to this device**, раскройте **Advanced** и отметьте **I am using an SSH tunnel to this local address**. Этот переключатель разрешает loopback-подключение; здесь адрес обслуживает локальный проброс Docker/WSL.
4. Нажмите **Add host using tunnel**; при отсутствии предупреждения кнопка может называться **Add host** или **Add Server**. Дождитесь **Connected** и откройте проект из списка слева.

Подключение Windows-клиента Orca к ADC в WSL проверено с локальным пробросом порта. Если подключение не удаётся, диагностика и команда проверки порта приведены в [справочнике среды](docs/workspace.md#диагностика-подключения-orca). Надпись **SSH tunnel required** отражает выбранный переключатель; **Manual update** означает, что сервер Orca обновляется вместе с ADC.

### Выбрать агента и поставить задачу

В **⚙️ → Agents** задайте **Default Agent** и оставьте включёнными **Agent status hooks**, чтобы видеть состояния сессий. Кнопка **Refresh** обновляет список обнаруженных агентов. Переключатель **Agent runtime: Windows / WSL** относится к локальному запуску; для проектов ADC место выполнения выбирается в поле **Run on**. Список **Installed** без пометки сервера может показывать агентов компьютера, даже если в ADC установлены дополнительные агенты.

1. Наведите на название проекта слева и нажмите **＋**, чтобы открыть **Create worktree**.
2. Проверьте **Project** и выберите **Run on → ADC Developer**.
3. В **Create From** выберите **Name** и введите название, например `check-tests`. Проверьте исходную ветку: обычно это `origin/main`; незакоммиченные изменения основного checkout в новый worktree автоматически не переносятся.
4. В **Agent** выберите Codex, Claude или другого установленного в ADC агента. Нажмите **Create worktree**.
5. Когда откроется сессия агента, отправьте описание задачи. Название worktree задаёт имя рабочего пространства; поручение агенту вводится отдельно.

Для первого запуска подойдёт задача без изменений:

> Прочитай AGENTS.md и документацию проекта. Найди и запусти доступные команды проверки. Пока ничего не изменяй. Расскажи, какие проверки прошли, какие упали и почему.

Вход в аккаунт агента выполняется внутри ADC. Успешный ответ с выполненными командами подтверждает работу агента через Orca. Проверить терминал можно командами `pwd`, `echo "$ADC_RUNTIME"` и `adc doctor project .`: ожидайте путь нужного checkout, `1` и отсутствие ошибок проверки.

Задачи можно давать агенту и в основном checkout проекта, открыв его **main** и выбрав агента в терминальной панели. Worktree удобен для отдельных изменений и параллельных задач: каждая задача получает свою ветку и каталог. После работы проверьте diff, закоммитьте нужные изменения и [перенесите результат в main](docs/workspace.md#перенести-результат-worktree-в-main).

### Что показывает Tasks

Раздел **Tasks** подключает внешние трекеры. Окно **New GitHub issue** создаёт задачу на GitHub, а поле **Assignees** выбирает пользователей GitHub. Ошибка **Could not resolve GitHub owner/repo for this repository** означает, что Orca не определила GitHub-репозиторий для выбранного проекта; например, remote на вашем Forgejo не становится GitHub-репозиторием. Источник задач выбирается в **Settings → Task Sources**, учётные данные соответствующего сервиса настраиваются в **Integrations**. Для собственного поручения агенту используйте описанный выше запуск worktree и сессии.

Названия элементов могут меняться между версиями клиента Orca. Официальные руководства: [подключение сервера](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/remote-servers.mdx), [первый запуск агента](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/first-session.mdx), [worktree](https://github.com/stablyai/orca/blob/main/docs/site/content/docs/model/worktrees.mdx).

## Возможности для проекта

Выберите возможности при подключении репозитория. В таблице `<path>` означает путь к проекту; несколько возможностей можно передать через запятую: `--capability pnpm-nx,changesets,frontend`.

| Возможность | Команда подключения | Что получает агент | Настройка MCP |
|---|---|---|---|
| `pnpm-nx` | `adc project add <path> --capability pnpm-nx` | Правила работы с pnpm/Nx и документ `MONOREPO.md` | Не требуется |
| `changesets` | `adc project add <path> --capability changesets` | Правила подготовки changeset, версий и релизов пакетов | Не требуется |
| `playwright` | `adc project add <path> --capability playwright` | Правила проектных e2e и браузер через Playwright MCP | Автоматически |
| `chrome-devtools` | `adc project add <path> --capability chrome-devtools` | Профилирование, анализ сети и производительности через Chrome DevTools MCP | Автоматически |
| `frontend` | `adc project add <path> --capability frontend` | Правила работы со скиллами фронтенда, Playwright MCP и Chrome DevTools MCP | Оба автоматически |
| `figma` | `adc project add <path> --capability figma` | Правила использования дизайна и Figma MCP | `adc mcp enable figma --project`, затем OAuth у агента |
| `graphify` | `adc project add <path> --capability graphify` | Полный скилл Graphify, CLI, локальный индекс кода и MCP для вопросов о связях | Автоматически; индекс обновляется ADC |
| `obsidian` | `adc project add <path> --capability obsidian` | Скилл работы с заметками и доступ к Obsidian MCP на компьютере | Открыть vault и включить Local REST API; `adc project capability add obsidian` спросит адрес и ключ |

В уже подключённом проекте команды работают на хосте и внутри ADC:

```sh
adc project capability list                 # каталог; зелёная ✓ у выбранных
adc project capability add graphify         # добавить и сразу доставить
adc project capability add frontend figma   # добавить несколько
adc project capability rm figma             # убрать из командного выбора
```

Выбор сохраняется в `.agents/project.json`; добавьте его в Git, чтобы команда использовала те же возможности. Команды определяют текущий checkout, включая worktree, сохраняют остальные настройки и автоматически запускают синхронизацию. Каталог доступен и без запущенного workspace; добавление подготовит инструменты в работающей среде. Если доставка завершилась ошибкой, выбор сохранён: исправьте причину и повторите команду добавления; ошибки конфигурации MCP можно исправить через `adc mcp doctor <имя> --fix`. Перезапуск workspace не нужен; откройте новую сессию агента после изменения MCP. Дополнительные настройки описаны в [справочнике](docs/workspace.md#возможности-и-проектные-настройки).

ADC сохраняет инструкции и конфигурацию самого репозитория. Выбранные возможности описывают правила работы агента; зависимости приложения устанавливаются по правилам проекта.

## Включить и проверить MCP

Запускайте команды из каталога подключённого проекта. Для `playwright`, `chrome-devtools` и `frontend` ADC сам подготавливает браузер и доставляет конфигурацию при запуске среды или синхронизации.

```sh
cd ~/Development/frontend
adc mcp list
adc mcp sync
adc mcp doctor             # реально проверить подключение и инструменты
```

Для Figma выберите возможность `figma`, затем выполните:

```sh
adc mcp enable figma --project
```

На запрос `FIGMA_MCP_ENABLED` введите `1`, затем авторизуйтесь через MCP-интерфейс выбранного агента. Для Codex команда синхронизации выводит отдельную инструкцию по добавлению сервера и входу.

Для Obsidian откройте нужный vault и включите Local REST API → Enable HTTP server. Затем выполните:

```sh
adc project capability add obsidian
```

CLI покажет требования, спросит адрес MCP `/mcp/`, доступный из контейнера, и API key из настроек плагина. Ввод ключа скрыт. ADC сохранит локальные настройки, проверит соединение и доставит MCP, инструкции и скиллы агентам Claude, Codex и OpenCode. Повторное добавление использует сохранённые параметры. Откройте новую сессию агента после доставки.

```sh
adc mcp doctor obsidian        # проверить авторизацию и список инструментов
adc mcp doctor obsidian --fix  # исправить адрес или ключ и проверить снова
```

`adc mcp list` показывает конфигурацию, `doctor` — реальное подключение. Ошибка проверки возвращает ненулевой код и объясняет причину; выбранная capability при этом остаётся сохранена. Требования, хранение секретов и ограничения сети описаны в [справочнике](docs/workspace.md#obsidian).

## Повседневные команды

В примерах `frontend` обозначает ID подключённого проекта.

| Задача | Команда |
|---|---|
| Показать подключённые проекты | `adc project list` |
| Открыть терминал проекта в среде | `adc workspace shell frontend` |
| Создать worktree для задачи | `adc worktree create frontend fix-validation` |
| Обновить инструкции и инструменты проекта | `adc sync frontend` |
| Обновить инструкции всех проектов | `adc sync --all` |
| Добавить агентам источник знаний | `adc project knowledge frontend docs/architecture.md 'Команда frontend'` |
| Проверить состояние среды | `adc workspace status` |
| Остановить среду с сохранением данных | `adc workspace stop` |
| Проверить установку | `adc doctor` |
| Проверить проект и ссылки без изменений | `adc doctor project frontend` или `adc doctor project /path/to/repo` |
| Узнать установленную ревизию | `adc --version` |
| Открыть справку по задачам Orca | `adc task --help` |
| Открыть справку по координации агентов | `adc orca orchestration --help` |
| Запустить панель OmniRoute | `adc omniroute serve` → http://localhost:20128 |
| Обновить граф кода текущего проекта | `adc tools graphify index` |
| Посмотреть все команды ADC | `adc --help` |

Новые подключения применяются командой `adc workspace start`. При изменении набора проектов контейнер пересоздаётся; сначала завершите или приостановите работу агентов. Исходники, worktree и сохранённые данные среды остаются на месте.

OmniRoute поставляется внутри среды как общий шлюз к моделям. Провайдеры подключаются в его панели; агенты используют шлюз после настройки их адреса API. Подробнее о Graphify и OmniRoute — в [справочнике среды](docs/workspace.md).
