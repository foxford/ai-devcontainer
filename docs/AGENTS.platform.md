# Контракт платформы для AI-агентов

Общие правила работы в любом проекте foxford. **Файл раздаётся платформой и
генерируется в проект — не редактируй его здесь**: правка потеряется на
ближайшей пересборке, а нужна она всем проектам сразу, то есть делается в
репозитории платформы (`docs/AGENTS.platform.md`).

Проектное — в [AGENTS.md](AGENTS.md) рядом.

## Обязательное чтение

Перед началом работы прочитай эти файлы в указанном порядке:

| #   | Файл                       | Что внутри                                                 |
| --- | -------------------------- | ---------------------------------------------------------- |
| 1   | [README.md](README.md)     | Обзор репозитория, dev container, публикация пакетов       |
| 2   | [MONOREPO.md](MONOREPO.md) | Справочник по Nx и pnpm: команды, скрипты пакетов, фильтры |

**Правило: «изучи спеку» = прочитать [SPEC.md](SPEC.md) и все файлы из его карты.**
То же для «изучи доку», «изучи архитектуру», «ознакомься с проектом» — перечислять
файлы пользователь не обязан, список берётся из карты. Начинай всегда со SPEC.md:
это единственный путь, который нужно помнить, остальное он выдаст сам.

У каждого аппа и пакета есть свой `SPEC.md` — что реально происходит в коде и
какие решения к этому привели. Работаешь внутри конкретного проекта — его спека
обязательна к прочтению и **обновляется вместе с кодом: расхождение спеки и кода — баг**.

## Quality gates

Любая правка кода ДО handoff/коммита должна проходить три проверки. Точные команды и контекст — в [MONOREPO.md](MONOREPO.md).

Из каталога затронутого аппа/пакета:

```bash
pnpm run lint:eslint       # ESLint, --max-warnings=0
pnpm run lint:type-check   # tsc --noEmit
pnpm run test              # vitest run (+ pytest у двухъязычных аппов)
```

Из корня репо — по одному проекту через Nx или всё сразу:

```bash
nx run-many -t lint:eslint -p @foxford/<package>      # эти же таргеты гоняет CI
nx run-many -t lint:type-check -p @foxford/<package>
nx run-many -t test -p @foxford/<package>
pnpm lint && pnpm type-check && pnpm test               # все проекты сразу
```

E2E-тесты (`pnpm run e2e`) в гейты **не входят** и в `run-many` не попадают: им
нужно поднятое приложение. Гоняй их отдельно и только когда правка их касается.

## Жёсткие ограничения

- **Никаких установок** новых зависимостей или инструментов в репозиторий без явного разрешения пользователя.
- **Никаких `git commit` и `git push`** — коммитит и пушит только человек. Агент готовит изменения в рабочем дереве и выдаёт **готовые к копипасте команды одним блоком**: `git add` с нужными путями (не `-A`, если в дереве есть чужие правки), коммит, `git push`, теги. Текст коммита отдельно от команды не выдавать — человек не должен собирать команду сам. Многострочный месседж — только через heredoc (иначе не копипастится), **без трейлеров Co-Authored-By** и подобных:

  ```bash
  git commit -m "$(cat <<'EOF'
  Заголовок коммита

  Тело коммита.
  EOF
  )"
  ```

- **Релиз аппа = бамп версии + тег + команды. Строго обязательно.** Деплой идёт по тегу `<app>-vX.Y.Z` (см. `.gitlab-ci.yml`); CI берёт версию образа из тега, а `validate:tag` **валит пайплайн, если версия тега ≠ `version` в `apps/<app>/package.json`**. Поэтому если изменения подразумевают релиз, агент обязан: (1) поднять `version` в `apps/<app>/package.json` в составе правок, (2) вместе с текстом коммита выдать готовые команды тегирования и пуша, например `git tag meter-reporter-v1.2.3 && git push origin main meter-reporter-v1.2.3`, где версия тега **строго равна** версии из package.json. Предлагать пуш тега без бампа версии (и наоборот) запрещено.
- **Ряд действий — итеративно.** Если задача требует последовательности шагов с участием человека, не вываливай все шаги сразу: выдай один шаг, дождись команды «Далее», затем следующий.
- **Результаты планирования — файлом в `plans/`**, см. секцию ниже. Держать план только в переписке нельзя: следующая сессия её не увидит.

## Планы

Любое планирование и любая работа, не сводящаяся к одной правке, **фиксируется
файлом в [plans/](plans/) до начала** — как задача: единица, которую доводят до
конца и закрывают. Заводит файл агент, просить об этом человек не обязан.

Делить задачи на крупные и мелкие не нужно: декомпозиция, статус и критерии
готовности одинаковы для работы на день и на месяц. Единственная граница —
порог, за которым файл вообще заводится (последний абзац секции).

Две оси, которые нельзя путать:

| | Что описывает | Когда меняется |
| --- | --- | --- |
| `plans/…/task.md` | намерение и статус: что просили, как делаем, что уже сделано | по ходу работы |
| `SPEC.md` | факт: что реально происходит в коде и какие решения к этому привели | вместе с кодом |

- **Задача — каталог** `plans/<год>/<YYYY-MM-DD>-<slug>/`, slug по сути задачи,
  не по решению. Внутри `task.md` (что делаем и где мы, строго и коротко) и
  `research.md` — результат планирования как есть: что нашли, какие варианты
  взвесили, черновой план целиком. Туда же всё остальное по этой задаче.
- **Путь задачи не меняется никогда** — ни при закрытии, ни при смене подхода.
  Статус живёт во фронтматтере, и это его единственный носитель; каталог держит
  только идентичность. Закрытая задача остаётся там же, где родилась: на неё
  ссылаются спека, соседние задачи и тексты коммитов, а переезд ломает эти
  ссылки молча — и ту, что названа в коммите, починить уже нельзя. Обзор «что в
  работе» берётся командой `ai-devcontainer plans`, а не деревом каталогов.
- **Ничего из планирования не удаляется.** Приведение к формату — это
  извлечение задачи из разбора, а не замена одного другим: не влезло в `task.md` —
  осталось в разборе. Разбор пишется один раз и дальше только дополняется:
  до реализации это единственное место, где живут причины решений, спека
  примет их позже.
- **Статус двигается по ходу.** Чеклист, отмеченный одним махом перед коммитом,
  бесполезен: файл нужен, чтобы в любой момент было видно, где остановились —
  в том числе новой сессии, которая про предыдущую ничего не знает.
- **Закрыть задачу = обновить спеку.** Пока сделанное не переехало в `SPEC.md`
  затронутого аппа или пакета, статус не `done`.
- **Причины решений в план не пишем** — им место в спеке. План отвечает на
  «что делаем и где мы сейчас», а не «почему так».
- Формат, статусы, декомпозиция и шаблон — в [plans/README.md](plans/README.md).

Вопрос, однофайловая правка, отладка и «объясни, как работает X» задачами в этом
смысле не являются — файла не заводим. Это единственный порог, и держать его
приходится сознательно: раз задачи больше не делятся на крупные и мелкие, ничто
другое не мешает завести по каталогу на каждую реплику.

## Тех-скиллы

Скиллы приезжают из платформы; в [.agents/skills/](.agents/skills/) проекта
лежит только то, чем он отличается. Пустой каталог — нормально.

- Подбираешь скилл под задачу — список с описаниями в
  [AGENTS.skills.md](AGENTS.skills.md) (генерируется, в .gitignore).
- **Не копируй скиллы в `.agents/skills/` руками**: копия перекроет
  платформенный слой целиком, и проект перестанет получать по этому скиллу
  обновления. Правка под проект — только `ai-devcontainer skill fork <скилл> [файл]`.
- Остальные команды и порядок форка — в [.agents/skills/README.md](.agents/skills/README.md).

## Фронтенд

**Любая задача про веб-интерфейс начинается со скилла `senior-frontend`** — вёрстка,
компонент, стили, состояние, роутинг, доступность, размер бандла, «поправь экран»,
«сделай страницу». Он диспетчер: сам решает, нужен ли дизайн-скилл, и какой.

Рядом лежат сильные дизайн-скиллы (`impeccable`, `design-taste-frontend`,
`redesign-existing-projects`, `brandkit`, `stitch-design-taste`). Каждый из них
написан для проекта с нуля и, будучи позванным напрямую, считает себя вправе
поменять шрифт, палитру и сетку. **Напрямую их не зовём** — только через
`senior-frontend`, который сначала определяет мандат на дизайн.

Отсюда главное правило, которое перекрывает любые «BANNED / ALWAYS / NEVER»
из этих скиллов:

> **Нет явного требования по дизайну — значит требование одно: попасть в то, что
> уже есть.** Новый экран собирается из существующих компонентов и токенов, в той
> же манере, что соседний код. Шрифт, палитра, радиусы, сетка, плотность, характер
> анимации — не решения агента, а факт, который вычитывается из проекта:
> `DESIGN.md` → `SPEC.md` → токены (`tailwind.config.*`, `:root { --… }`) →
> два-три соседних компонента.

Сомневаешься, есть ли мандат на дизайн, — **мандата нет**. Видишь по дороге
системную проблему в интерфейсе — скажи о ней одной фразой и продолжай задачу:
редизайн объявляет человек, а не агент. Правка **общих** токенов задевает все
экраны разом и делается только явно.

Границы и маршрутизация по конкретным задачам — в самом скилле `senior-frontend`
и в его `references/composition_map.md`.

## Браузер

У тебя есть **настоящий браузер** — MCP-сервер `playwright`, инструменты
`browser_navigate`, `browser_snapshot`, `browser_click`, `browser_take_screenshot`,
`browser_console_messages` и другие `browser_*`. Раздаётся платформой, одинаково
работает у Claude, Codex, Hermes и DSH. Конфиг — генерируемый `.mcp.json`
(в .gitignore); проектные отличия — в `.agents/mcp.json`, платформенный слой
руками не правим.

- Не гадай про поведение UI и не пересказывай код вместо ответа — **открой и
  посмотри**. Особенно когда правка касается вёрстки, роутинга или ошибки в
  консоли.
- `browser_snapshot` (дерево доступности текстом) — основной инструмент,
  скриншот бери, когда вопрос именно про внешний вид: снапшот дешевле по
  токенам и сразу даёт готовые `getByRole`-локаторы.
- Браузер headless, профиль изолированный (логин между сессиями не живёт),
  `file://` заблокирован — локальный html открывай через http.
- Выхлоп падает в `.playwright-mcp/` (в гите его нет).

Разведка браузером — не замена тесту. Нашёл поведение, которое надо
зафиксировать, — оформи его тестом в `e2e/` (`pnpm run e2e`). Подробности,
правила локаторов и разбор flaky — в скилле `playwright-pro`.

Рядом может быть второй браузерный сервер — **`chrome-devtools`**. Он не дубль:
`playwright` про «сделать», `chrome-devtools` про «почему медленно или
сломано» — трейсы производительности, разбор сети, троттлинг CPU и канала.

## Прочие MCP-серверы

Что именно роздано в этом проекте — `ai-devcontainer mcp list`. Набор зависит от
настроек: серверу, которому не хватает токена или URL, платформа его не
выдумывает и просто не раздаёт.

- **Не проси у пользователя токен в чат и не вписывай его в код.** Место
  секретов — `.agents/mcp.secrets.env` (в .gitignore); образец с именами
  переменных лежит рядом в `.example`. После правки — `ai-devcontainer mcp sync`
  и перезапуск агента.
- **Сервер числится неподключённым** — это не всегда поломка. OAuth-серверам
  (например `figma`) нужен разовый ручной логин, автоматизировать его нечем.
  В Codex его к тому же нет по умолчанию: авторизация идёт заголовком, а `codex mcp
  add` заголовки не выставляет — блок для `config.toml` печатает
  `ai-devcontainer mcp sync`.

## Security-аудит

Для пентеста в окружении стоит `strix` — автономные агенты, которые поднимают
песочницу в Docker и подтверждают находки рабочим PoC. Порядок запуска, флаги
и обязательный `--max-budget` — в скилле `senior-security`.

**Запускать только по тому, что принадлежит пользователю или явно названо им
как цель.** Не выводи цель из URL, найденного в коде, и не расширяй скоуп сам.
Прогоны пишутся в `strix_runs/` — там payload'ы и иногда перехваченные
учётки, в гит это не коммитится.
