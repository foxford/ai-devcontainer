# Архитектура ADC

## Назначение и границы

ADC подключает существующие репозитории к общей рабочей среде разработчика. CLI написан на Go: точка входа и дерево команд в `bin/adc/`, хостовые операции в `bin/adc/host/`, доставка внутри контейнера в `bin/adc/runtime/`, общие операции в `bin/adc/internal/`. Дерево команд, справку и автодополнение формирует Cobra v1.10.2. ADC работает как бинарник.

Хост управляет Docker, установкой, регистрацией проектов и обновлением клона платформы. Доставка инструкций и настройка агентов выполняются внутри Linux-контейнера. Переменная `ADC_RUNTIME=1` обозначает эту границу. Установка инструментов, entrypoint, баннер, адаптеры агентов, архивы и вспомогательные утилиты также реализованы на Go. Shell нужен для bootstrap, экспорта окружения, проектного motd и официальных vendor-installers.

## Установка

POSIX- и PowerShell-скрипты устанавливают Git и средства загрузки, скачивают закреплённый Go с проверкой SHA-256 в `ADC_HOME/toolchains`, клонируют или обновляют платформу и собирают CLI. Команда `adc install` размещает бинарник, настраивает PATH и автодополнение, проверяет и устанавливает Docker, устанавливает Orca на хост и создаёт конфигурацию среды.

adc completion <bash|zsh|fish|powershell> сохраняет скрипт и печатает путь и команды подключения, сохраняя профили пользователя без изменений. Генератор Cobra общий с InstallShell; --stdout явно выводит сырой скрипт, --no-descriptions управляет описаниями. Bash/Zsh/PowerShell используют ADC_HOME/completions на хосте и отдельный ~/.local/share/adc/completions в runtime, чтобы сокращённое дерево runtime не заменяло хостовые команды. PowerShell использует имя adc.ps1 в установщике, bootstrap и ручной команде. Fish устанавливается в XDG_CONFIG_HOME/fish/completions с fallback ~/.config/fish/completions; Zsh-инструкции учитывают ZDOTDIR и compinit. Пути в командах подключения экранируются для соответствующей оболочки.

Установщик сообщает, если ОС требует UAC, повторный вход или перезагрузку. В профилях оболочек он меняет только управляемые блоки. adc update до Git pull проверяет локальные изменения платформы и незавершённое переключение workspace. Новый CLI собирается во временный исполняемый файл и запускается для обновления образа, команды, completion и Orca. Ошибка компиляции сохраняет прежний бинарник; клон после успешного pull уже может содержать новую версию. Helper проверяет текущий workspace и до остановки подготавливает образ, параметры запуска, seccomp/AppArmor и установку CLI. Отсутствующий, созданный или остановленный контейнер сам не запускается. Приостановленный контейнер требует явного unpause. Перезапуск завершает активные сеансы агентов; постоянные тома и регистрации проектов сохраняются. На Windows работающий прежний exe переименовывается перед заменой; если процесс ещё держит файл, его копия остаётся в ADC_HOME/bin/.adc-previous-*.exe.

Docker build публикует ID именно своего образа через временный --iidfile; запуск использует этот ID вместо изменяемого adc-runtime:local. Ключ контейнера сохраняет совместимость с прежним форматом. Host update/start/stop используют отдельный lifecycle.lockfile; исходники на время pull/build/helper и start защищает update.lockfile. Runtime продолжает брать write.lockfile для доставки, поэтому ожидание готовности не блокирует синхронизацию. Блокировки освобождаются при завершении процесса.

У каждой поставляемой единицы skill, document, MCP и bundle есть метафайл с kind, name и version по SemVer. Скиллы и бандлы хранят meta.json в своём каталоге; MCP хранит <name>.meta.json рядом с файлом определений серверов. Инструкции и доставляемые документы используют kind: document и метафайл <полное-имя-файла>.meta.json рядом с исходником; один исходник, используемый несколькими возможностями или одновременно как инструкция и документ, имеет одну версию. Версия содержимого независима от version: 1 в bundle.json, обозначающей формат манифеста. Разработчик повышает версию изменённой единицы явно. Равная или более старая опубликованная версия не считается обновлением; содержимое файлов не сравнивается. Состав метафайлов сверяется с каталогом Go-тестом.

Команда adc updates доступна на хосте и в runtime, --refresh обходит кеш, --json выводит данные без цвета. Хостовая adc update --check выполняет ту же проверку без применения. ADC читает tracking remote и ветку платформы, получает метафайлы через отдельный Git-кеш в ADC_HOME/cache/updates и сравнивает опубликованные версии с локальными. Для публичного foxford/ai-devcontainer проверка преобразует стандартный GitHub SSH URL в HTTPS только в своих Git-командах; SSH-ключи и known_hosts для неё не нужны. Точное правило insteadOf на время команды сохраняет HTTPS при пользовательском общем перенаправлении GitHub на SSH. Remote клона и транспорт других репозиториев, включая приватные форки, сохраняются. Смена адреса проверки отменяет прежнюю кешированную SSH-ошибку. Кеш успешной проверки действует сутки, ошибки — час; автоматическая проверка при интерактивном workspace start/shell и в runtime banner ограничена тремя секундами, явная — пятнадцатью. Ошибка сети не прерывает открытие среды. Основной checkout, его refs и файлы проектов проверкой не изменяются. Уведомление предлагает adc update --delivery; полное обновление среды выполняет adc update на хосте. В терминале доступные версии выделены жёлтым, успешное обновление платформы — зелёным, ошибка явной проверки — красным; NO_COLOR, TERM=dumb, перенаправленный и JSON-вывод не содержат ANSI. Отчёт после adc update сравнивает версии до и после успешного helper в памяти, без журнала доставленного состояния.

`adc update --delivery` работает на хосте и в runtime: получает опубликованную ревизию tracking-ветки, извлекает из неё каталог delivery и проверяет его источники и метафайлы, затем применяет доставку без сборки CLI или Docker-образа и без перезапуска контейнера. Получение официального репозитория использует HTTPS, как проверка версий. Git-клон платформы и его refs сохраняются. Получение файлов ограничено двумя минутами; архив допускает только каталоги и обычные файлы внутри delivery, сохраняет исполняемые биты и ограничен 20 000 записями, 16 MiB на файл и 128 MiB суммарно. До активации проверяются формат каталога, ссылки на источники и версии. Более старая версия уже установленной единицы отклоняется.

При проверке версий и загрузке доставки ADC дочитывает stdout git archive до конца потока перед ожиданием завершения процесса. После маркера конца tar Git дописывает выравнивающие байты; непрочитанный остаток мог блокировать процесс на Windows. Ошибка чтения этого остатка возвращается вызывающей команде. Go-тест воспроизводит блокировку через канал без буфера для обоих режимов загрузки и проверяет передачу ошибки потока.

Скачанные файлы хранятся в `ADC_HOME/delivery/<revision>/delivery`. Атомарный `current.json` содержит ревизии доставки и исходной платформы; `DeliveryPath` выбирает этот источник для каталога, инструкций, документов, скиллов, MCP и проверки обновлений. При смене ревизии платформы после полного обновления используется её каталог delivery. Прежние каталоги сохраняются для существующих ссылок. Это хранение самих файлов доставки, без журнала применения по проектам и без сравнения контрольных сумм содержимого: уведомления по-прежнему сравнивают только версии метафайлов.

Получение и применение доставки защищены update.lockfile, общий Git-кеш — check.lockfile, переключение источника и запись агентных конфигов — write.lockfile. Ошибка загрузки или проверки сохраняет прежний источник. Ошибка применения оставляет новый источник доступным и возвращает ошибку с командой повтора; повторный adc update --delivery снова применяет ту же версию. На хосте работающий workspace получает доставку через docker exec; остановленный, отсутствующий или приостановленный контейнер не запускается и получает её при следующей подготовке workspace или агента. Активные сессии агентов сохраняются; новые инструкции и MCP следует читать в новой сессии.

`sync` остаётся внутренней командой для setup hooks, адаптеров агентов и совместимости существующих установок; она скрыта из публичной справки и автодополнения. Пользовательское обновление доставки само запускает применение. Внутренний sync --all обрабатывает зарегистрированные проекты и существующие Git worktree из их реестров, проверяя совпадение Git common dir. Явно зарегистрированный checkout сохраняет собственные настройки, включая read-only; недоступные и чужие worktree пропускаются. Read-only проекты не изменяются. Документы ADC обновляются копированием или заменой управляемой ссылки согласно каталогу; файлы проекта без маркера или управляемой ссылки сохраняются, AGENTS.md и CLAUDE.md получают только управляемые блоки.


При замене существующего контейнера ADC до остановки атомарно записывает ADC_HOME/workspace-replacement.json: ID прежнего контейнера, исходное работающее состояние, старый и новый ключи, имя резервного контейнера и случайный token. Аргументы Docker и секреты в журнал не входят. Прежний контейнер останавливается и переименовывается в adc-<workspace>-previous-<token>; новый получает label adc.replacement. После подтверждения ready прежний контейнер удаляется без force, затем удаляется журнал. Ошибка Docker run восстанавливает прежнее имя, ключ и исходное работающее состояние; ошибка восстановления оставляет журнал. Ошибка runtime-подготовки или очистки и прекращение ожидания через Ctrl+C также сохраняют журнал и прежний контейнер. Повторный workspace start сверяет настоящие ID и label, восстанавливает незавершённый переход до создания либо продолжает подготовку уже созданного runtime. Неудачная подготовка кандидата при повторе запускается заново. Чужие или неожиданно запущенные резервные контейнеры автоматически не удаляются. Status сообщает о журнале даже при отсутствующем основном контейнере. Содержимое общих томов, проектная доставка, клон платформы и установленный CLI этим механизмом не откатываются.

Повторный start неизменившегося контейнера тоже проверяет состояние подготовки и перезапускает runtime с failed, включая неудачный первый запуск без журнала переключения. Готовый контейнер при обычном start сохраняется; update пересоздаёт работающий контейнер даже при неизменившемся образе, чтобы обновить runtime и завершить активные сеансы.

Сценарии переключения покрыты Go-тестами ошибок и прерываний. Docker smoke проверяет отказ run с отсутствующим образом и потерю ответа после успешного rename; оба сценария прошли в CI на ревизии b32c907.

Orca v1.4.223 закреплена в `runtime/orca-lock.json`; пакеты проверяются до установки. Хостовое приложение подключается к `orca serve` в контейнере. Сервер поставляется в составе официального Electron-приложения; ему нужны библиотеки Electron и Xvfb. AppImage распаковывается при сборке без FUSE.

`runtime/Dockerfile` собирает один образ `adc-runtime:local`: тулчейн, ADC, Orca, Bash и Zsh с oh-my-zsh. Отдельная база dev-base не требуется. Контекст сборки ограничен `.dockerignore`; доставляемые материалы и shell-env подключаются read-only маунтом платформы. Внутренние движки входят в Go-бинарник образа.

Окружение login- и interactive-оболочек задаёт `runtime/shell-env.sh`. История Bash/Zsh сохраняется в общем home, в `.history/`. Go-команда `adc banner` показывает имя среды и команды ADC; текущий checkout может дополнить его через `.agents/motd.sh`. Корень ищется по `.git`, включая файл worktree. Общий баннер входит в бинарник образа и требует пересборки; проектный `.agents/motd.sh` применяется в следующем терминале без сборки.

Образ сохраняет стандартные профили Bash/Zsh и oh-my-zsh также в `/opt/adc-shell`, вне тома home. При подготовке ADC восстанавливает отсутствующий oh-my-zsh и профили без пользовательского содержимого, включая созданные прежним initializer профили с одним управляемым блоком. Существующие настройки и framework сохраняются; управляемый блок подключает окружение, историю, метку workspace в prompt Zsh и баннер терминала. Это работает и для непустого home, созданного импортом с `volume-nocopy`.

Если установщик уже добавил PATH или комментарии в `.zshrc`, ADC сохраняет этот профиль и подключает oh-my-zsh с Powerlevel10k в своём блоке, когда framework ещё не загружен и prompt остался стандартным `%m%# `. Явные тема и plugins сохраняются; загруженный framework и пользовательский prompt не заменяются. Начальная настройка Powerlevel10k не открывает интерактивный мастер.

`adc doctor project .` сопоставляет канонический абсолютный путь checkout с реестром. Доставка DSH заменяет свои старые ссылки `/workspaces/<checkout>/.claude/skills/<skill>` на относительные ссылки внутри проекта; ссылки на уже не выбранные скиллы удаляются только при совпадении с известным управляемым путём. Чужие ссылки сохраняются.

Doctor канонизирует также зарегистрированные пути, чтобы алиасы каталогов, включая `/var` и `/private/var` на macOS, сохраняли идентификатор и read-only статус проекта. Smoke проверяет наличие worktree до перезапуска и его сохранность после штатной остановки и пересоздания контейнера; принудительное убийство процесса не подменяет обычный lifecycle в этой проверке.

`adc skill list`, `adc skill status` и текстовый `adc mcp list` выводят таблицы с заголовками и выровненными пробелами колонками. У MCP слой, статус конфигурации и причина недоступности показаны отдельно; включённый сервер не объявляется проверенным соединением. JSON-вывод MCP сохраняет прежний формат.

Скрипт zsh-in-docker фиксированной версии скачивается через curl с проверкой TLS, повторами при сетевых ошибках и ограничениями времени. Установщик запускается только после успешной загрузки непустого файла; обрыв TLS не запускает частично скачанный скрипт. Его вложенные curl используют временный CURL_HOME: 20 секунд на соединение и 60 секунд на одну загрузку, с отказом при ошибке HTTP. Общего таймаута установки нет; временная конфигурация не попадает в пользовательский home.

## Рабочая среда и реестр

Общий skill humanizer содержит полную поставку humanizer-ru 3.31.4 с локальными исправлениями русского тире, жанровых исключений и примеров, сохраняющих смысл. В него входят справочники, Python-сканер и requirements.txt с razdel 0.5.0 и pymorphy3 2.0.6. Скилл запускает свою копию сканера через изолированный uv run без загрузки настроек и зависимостей приложения. Специальной команды или установщика humanizer в Go нет. Сканер показывает совпадения с правилами и изменения извлечённых фактов; семантическая эквивалентность и авторство этим не устанавливаются. Общий контракт AGENTS.platform.md направляет редактуру русского текста и финальную вычитку собственных черновиков к доступному humanizer. Для русского README при наличии обоих скиллов сначала применяется readme-writer, затем humanizer; факты, технический регистр, код и цитаты сохраняются.

`ADC_HOME` по умолчанию указывает на `~/.adc`, `AI_DEVCONTAINER_HOME` на клон платформы. Файл `workspace.json` версии 1 содержит поля `name`, `port`, `omniroutePort`, `graphPort`, `projects` и `knowledge`.

Запись проекта содержит `id`, `path`, `runtimePath`, `description`, `capabilities`, `related`, `knowledge` и `readOnly`. Автоматический ID включает хеш абсолютного пути, поэтому одинаковые имена каталогов не совпадают. Пользователь может задать ID явно. Имена среды и проектов валидируются; повторные и вложенные маунты отклоняются.

Каждый проект и каталог состояния подключаются отдельными bind-маунтами; платформа доступна только для чтения. Домашний каталог, AI-инструменты и `/workspace` сохраняются в томах `adc-<name>-{home,tools,worktrees}`. Orca хранит метаданные в `/home/node/.config/orca`, worktree в `/home/node/orca/workspaces`; оба пути входят в том домашнего каталога.

Docker socket и домашний каталог хоста не монтируются. По умолчанию новые workspace публикуют Orca на `127.0.0.1:6770`, OmniRoute на `127.0.0.1:20128`, просмотр графа на `127.0.0.1:4242`. Внутренние порты остаются 6768, 20128 и 4242; хостовый порт Orca передаётся в ADC_ORCA_PORT для адреса подключения. Стандартный хостовый порт ADC отделён от 6768 десктопного сервера Orca. Существующие конфигурации, включая port: 6768, автоматически не меняются. На Unix пути проектов на хосте и внутри среды совпадают ради абсолютных Git-ссылок. На Windows проект доступен по `/workspace/projects/<id>`; подключение worktree с хостовыми Git-путями отклоняется.

Хостовая команда workspace config без флагов показывает сохранённые порты. Флаги --port, --omniroute-port и --graph-port меняют только явно переданные значения; диапазон и пересечение портов проверяются до записи. Настройка не требует доступного Docker и сохраняет имя, проекты и знания. Изменение выполняется под lifecycle.lockfile и write.lockfile с повторным чтением конфигурации; незавершённая миграция или переключение контейнера блокируют запись. Следующий workspace start применяет новые пробросы штатным пересозданием контейнера; перед запуском он перечитывает конфигурацию под lifecycle.lockfile. Команда init по-прежнему создаёт только новый workspace.

Docker получает встроенный seccomp-профиль на основе Moby default-deny с разрешениями unshare, mount, umount2, pivot_root и clone с CLONE_NEWUSER для вложенного bubblewrap Codex. Host capabilities не добавляются; setns и остальные привилегированные syscalls сохраняют ограничения upstream. Профиль записывается в ADC_HOME/security по SHA-256, его путь входит в ключ контейнера, поэтому обновление политики пересоздаёт среду при workspace start/update. Docker smoke проверяет user namespace; режим реальных инструментов дополнительно проверяет чтение документов и запись в проект через native Codex sandbox с запретом записи за пределами проекта. Глобальные sysctl и настройки разрешений пользователя Codex не изменяются.

Если Docker сообщает активный AppArmor, ADC загружает отдельный профиль `adc-runtime-<SHA256>` через уже установленный хостовый `apparmor_parser` и передаёт его конкретному контейнеру. Основа — Moby той же ревизии, что seccomp; разрешены mount и pivot_root при сохранении ограничений `/proc`, `/sys`, сигналов и ptrace. При первой загрузке и после перезагрузки хоста могут потребоваться права sudo; уже загруженный enforce-профиль повторно не загружается. Ошибка загрузки останавливает запуск среды. Поддерживается локальный Linux Docker host с AppArmor; ADC не устанавливает новые хостовые пакеты и не меняет профиль Docker глобально. На хостах без Docker AppArmor этот шаг пропускается. Работа под AppArmor требует подтверждения реальным smoke на хосте с включённым AppArmor; текущая WSL-среда его не включает.

Системный `bubblewrap` включён в Docker-образ по разрешению пользователя от 2026-10-11. Native Codex smoke использует изолированный `CODEX_HOME` в `/home/node/.cache`, чтобы Codex мог создать PATH launcher; тест проверяет наличие системного bwrap, чтение/запись внутри sandbox и отсутствие предупреждений о missing bubblewrap или запрете helper binaries в `/tmp`.

Команда `workspace start` собирает образ, сравнивает аргументы маунтов и ID образа, затем запускает существующий контейнер или пересоздаёт его. Остановка и пересоздание завершают живые процессы, сохраняя файлы и историю. Маркер `/tmp/adc-ready` появляется только после успешной доставки и регистрации проектов; фоновая индексация Graphify не входит в условия готовности. При смене UID владельцы home и tools определяются отдельно: usermod может изменить home раньше, чем общий том инструментов. Переназначение прав не проходит через симлинки в другие маунты.

## Контекст, возможности и скиллы

`delivery/catalog.json` версии 1 задаёт базовые инструкции и документы, источник скиллов, источник и список платформенных MCP. Простая возможность добавляет инструкции, документы и имена серверов. Бандл регистрируется через `bundle`, а его `bundle.json` декларирует `exports.instructions/skills/documents/mcp/tools`. Graphify и Obsidian доставляются как бандлы. Источники exports разрешаются относительно бандла; CLI-версия Graphify задана в его exports.tools. Go проверяет пути и имена; автодополнение читает тот же каталог.

Все пути источников отсчитываются от `delivery/`, путь `target` документа от корня проекта. Каталог проверяет наличие каждого источника, его тип и соответствие имён MCP определениям, включая невыбранные возможности. Симлинк источника не может выходить за пределы `delivery/`. Структура материалов описана в [delivery/README.md](delivery/README.md).

Одна возможность может поставлять несколько MCP: `frontend` объединяет Playwright и Chrome DevTools. Повторяющиеся инструкции и серверы удаляются. Несовместимости из `conflicts` проверяются до записи в проекты.

Отпечаток исходников Graphify читает NUL-разделённые пути из Git и проверяет их как локальные пути текущей ОС. Допустимые Unix-имена с двоеточием, включая каталоги динамических маршрутов `:events`, индексируются и учитываются при изменениях tracked и untracked файлов. Для архивов и файлов доставки остаётся отдельная строгая проверка относительных путей.

Общий контракт находится в `delivery/instructions/AGENTS.platform.md`, инструкции возможностей в `delivery/instructions/capabilities/`. Выбор из регистрации дополняет командный выбор в `.agents/project.json`. Доставка сохраняет зависимости и стек проекта. Файл `AGENTS.platform.md` доставляется копией с маркером; `AGENTS.md` и `CLAUDE.md` сохраняют ручной текст и получают управляемые ссылки и импорты.

`adc project capability list` выводит каталог с описаниями и MCP, отмечая эффективный выбор текущего зарегистрированного checkout; в терминале галочки зелёные, `NO_COLOR` и перенаправление отключают ANSI. `add` и `rm` изменяют только массив `capabilities` в `.agents/project.json`, сохраняют прочие поля и права файла, проверяют всю композицию до атомарной записи под lock и сразу запускают `sync`. Команды доступны на хосте и внутри runtime, разрешают текущий worktree по Git common dir и отклоняют read-only проекты и перенаправляющие ссылки конфигурации. Возможности из регистрации не удаляются командной правкой; ошибка доставки оставляет выбранную конфигурацию; после исправления нужно повторить команду изменения возможности.

Карта `/workspace/AGENTS.workspace.md` перечисляет все проекты: назначение, права, связи и источники знаний с датой регистрации. Агент использует карту для выбора контекста по задаче. На неё ссылаются общие инструкции Claude, Codex и Hermes, а также проектные точки входа.

`project relate` подтверждает запись направленной связи и предлагает обновить карту; `workspace map` сообщает путь обновлённого документа.

Скиллы собираются из `delivery/skills/` платформы и `.agents/skills` проекта в `.claude/skills`. Проза подключается ссылками, код копируется, чтобы относительные импорты учитывали проектные форки. Общий каталог Codex получает платформенные скиллы независимо от порядка синхронизации. Адаптер проектного скилла получает уникальное имя из ID проекта и хеша пути checkout и направляет агента к собранному варианту этого checkout. Дерево DSH находится внутри проекта.

Общий скилл readme-writer поставляет полные инструкцию и шаблон NASA-AMMOS/slim (slim-readme, commit 46138b07c80798b3b80ec13feca6782e4b84870e) с локальной рамкой ADC и meta.json версии 1.0.0. Он создаёт и актуализирует README по фактам репозитория, сохраняет правила и язык целевого проекта, выбирает команды по реальному стеку и не требует обязательных разделов из шаблона. Скриптов, MCP и дополнительных зависимостей у скилла нет. Общий контракт AGENTS.platform.md направляет создание и содержательное обновление README к доступному readme-writer с приоритетом проектного варианта; отсутствие скилла не блокирует работу по правилам проекта.

## MCP

Списки `base.mcp.servers` и `capabilities.<имя>.mcp` фильтруют только платформенный слой перед слиянием. Общие определения находятся в `delivery/mcp/servers.json`, определения бандлов — в их экспортируемых MCP-файлах; одинаковые имена из разных источников отклоняются. `x-requires` дополнительно проверяет доступность браузера или секрета. Chromium для MCP устанавливается в сохраняемый кеш из закреплённого пакета Playwright MCP, независимо от зависимостей репозитория.

Go-движок MCP рекурсивно объединяет слои `global/user/project/local`, поддерживает отключение через `null`, условия `x-requires`, метку `x-oauth` и подстановку секретов. План для команды `list` не содержит раскрытых секретов.

Подстановки `REPO_ROOT`, `ADC_HOME` и `AI_DEVCONTAINER_HOME` разрешаются из текущего checkout и приложения ADC после чтения секретов. Graphify явно доставляет `ADC_RUNTIME=1` и пути состояния/платформы в env своего stdio MCP: запуск из Codex CLI и Codex Chat Orca не зависит от наследования переменных родителя. Codex ограничивает наследуемое окружение MCP; прямой запуск сервера с полным Docker env не проверяет этот сценарий. Docker smoke дополнительно запускает доставленную команду Graphify через `env -i` и выполняет initialize/tools/list.

Перед записью имена серверов получают префикс checkout. Очистка его старых записей сохраняет записи соседей; управляемый блок DSH также принадлежит конкретному checkout. Слияние Hermes сохраняет остальные серверы. Драйверы Claude/Codex/OpenCode/Hermes/DSH реализуют общий интерфейс подготовки конфигурации и параметров запуска; после подготовки всех драйверов общие записи выполняются под lock. Codex настраивается через его CLI; секретные HTTP-заголовки дописываются в приватный TOML без передачи в argv. Управляемые блоки заголовков отслеживаются в `.adc/mcp-state.json`, обновляются при ротации ключа и очищаются вместе со stale сервером; существующие ручные блоки сохраняются. Учитывается CODEX_HOME. OpenCode получает отдельный `.adc/opencode.json` с MCP и инструкциями checkout через inline-слой адаптера; пользовательский inline-конфиг имеет приоритет, обычные JSON/JSONC не переписываются. Пользовательский `.mcp.json` Claude остаётся без изменений; адаптер сессии подключает дополнительный `.adc/claude-mcp.json`. OAuth авторизуется в самом агенте; автоматическая авторизация при подготовке среды не выполняется.

Файл `ADC_HOME/write.lockfile` обеспечивает системную блокировку записи реестра и общих конфигураций агентов: `flock` на Unix и `LockFileEx` на Windows. При завершении процесса ОС освобождает блокировку. Go записывает файлы через временный файл, синхронизацию и переименование; совпадающие данные не переписываются. Файл блокировки сохраняется, чтобы процессы не могли заблокировать разные inode после его удаления.

Бандлы могут объявлять `activation.server/requirements/prompts`. Адрес и секретные env-параметры задаются явно; каталог отвергает неизвестный сервер, повторяющиеся/недопустимые вопросы и секретные defaults. `project capability add` выполняет мастер в runtime с TTY, сохраняет URL в local MCP-слое и ключи в проектном secrets.env с правами 0600, проверяет соединение и продолжает sync только при успешной проверке. Повторное добавление использует сохранённые настройки; прерванный ввод не записывает новые параметры. Выбор возможности и завершение активации различаются; сетевой сбой возвращает ошибку, не отменяя выбор. Первым бандлом с вопросами является Obsidian. Обычный startup/sync не задаёт вопросов и не проверяет соединение с личным vault.

`adc mcp doctor [name]` проверяет включённые MCP текущего checkout через initialize/notifications/initialized/tools/list, без вызова инструментов. HTTP поддерживает JSON/SSE, заголовки, session id, pagination и TLS verification; перенаправления не получают ключ. Stdio использует команду, env и cwd определения; процесс завершается после проверки. На сервер отводится 20 секунд; ответы ограничены 2 MiB и 100 страницами. Диагностика не выводит тела HTTP или сообщения ошибок сервера с возможными секретами. `--fix` спрашивает параметры активации или недостающий env-секрет и повторяет доставку и диагностику. Ввод и сетевые проверки выполняются вне общего lock; Graphify не переиндексируется диагностикой. Проверка MCP транспорта не проверяет аккаунт модели или результат агентной задачи.

## Orca, агенты и worktree

README содержит маршрут подключения хостового клиента Orca к ADC: runtime pairing URL, разрешение loopback через UI-переключатель локального туннеля, выбор Run on для ADC и запуск агента в worktree. В пользовательском сценарии Windows-клиент подключён к ADC в WSL через 127.0.0.1:6768; подтверждены список проектов, терминал внутри ADC, успешный doctor и запуск Codex с ответом и выполнением команд. Итог проектных тестов этим не подтверждается. Диагностика порта, обновление сервера из образа и слияние ветки задачи описаны в docs/workspace.md.

Go-entrypoint `runtime-serve` согласует UID/GID node, запускает Orca, ждёт готовности и вызывает `runtime-init`. Владельцы подключённых исходников не меняются. Команда `runtime-init` устанавливает штатные CLI-инструменты в сохраняемые домашний каталог и том инструментов, доставляет контекст, регистрирует checkout через `orca repo add` и создаёт `/tmp/adc-ready`. Worktree создаётся через `orca worktree create`, затем ADC синхронизирует результат. Внутренние SQLite-базы и настройки Orca не редактируются.

ADC сохраняет прежние setup-команды и комментарии в `orca.yaml` и добавляет свой блок. Исходная копия YAML находится в `.adc/backups`. YAML читает Go-парсер go.yaml.in/yaml/v3 v3.0.5. Запуск агентов ожидает завершения setup через `wait-for-setup`. Новый worktree может не получить незакоммиченный `orca.yaml`.

Пять штатных CLI запускаются через адаптеры в `/opt/adc-agents`. Адаптер — ссылка на тот же Go-бинарник ADC. Он определяет текущий Git checkout и вызывает синхронизацию перед настоящим CLI из каталога AI-инструментов. Административные вызовы `mcp/auth/version/help` и режим `ADC_DELIVERY` пропускают эту подготовку, чтобы избежать рекурсии.

Установщик CLI получает PATH без адаптеров: иначе поиск CLI принял бы адаптер за установленного агента. Тест подставляет PATH с адаптером и проверяет, что первым элементом результата стал каталог настоящих CLI, с нативными разделителями путей ОС. Профили оболочек подключают путь адаптеров последним управляемым блоком.

Orca управляет orchestration, task и worker; ADC передаёт соответствующие команды. Run сохраняет область выполнения, но сам не запускает планировщик. Hermes устанавливается как обычный агент вместе с Claude Code и Codex. Запись во внешний трекер и использование аккаунтов разработчика требуют поручения пользователя. Тестовые проекты обходятся без них.

## Исследование процесса разработки в Orca

Закреплённая Orca v1.4.223 предоставляет Workspace Board с настраиваемыми статусами карточек; CLI worktree set поддерживает --workspace-status и --comment. Это отдельная модель от состояний агентов в Agent Dashboard и Task/Dispatch в orchestration. Изменение колонки является изменением метаданных и само по себе не запускает этап и не проверяет тесты или аудит.

В ADC пока нет движка последовательных этапов разработки, журнала доказательств прохождения гейтов и связи этих гейтов с завершением пользовательской задачи. По требованию пользователя целевая машина состояний и планировщик реализуются программно на Go в ADC: движок хранит состояние, запускает исполнителей, проверяет результаты, выбирает разрешённые переходы и управляет повторами. Агенты выполняют поручения этапа и возвращают артефакты; AGENTS.md и skills объясняют исполнение, но не управляют переходами. Штатные поверхности Orca используются для исполнения и визуального управления; Workspace Board отображает проекцию состояния ADC. Плагин пока не выбран; автоматизация пользовательских колонок, реакция на ручной drag, восстановление после полного перезапуска runtime и мобильная проверка на другом хосте требуют отдельного прототипа. Агент-координатор не является допустимой заменой программного движка. Источники, ограничения и план проверки: [исследование workflow](plans/2026/2026-10-11-orca-workflow-integration/research.md).

Изолированное исследование программного управления подтвердило на реальном Orca v1.4.223, что Go-процесс в собственной Orca pane создаёт Run/Task без агента-координатора. Проверены replay запроса, failed worker_done от детерминированного unsupervised исполнителя, FIFO Delivery, rebind Run новым контроллером, consumer fencing и отказ позднему противоположному отчёту. Это не проверка настоящего supervised Claude/Codex, paired desktop UI или полного рестарта runtime. Сам ADC workflow engine не реализован. Запись workspaceStatus completed после failed Task успешно выполнена: строгие визуальные гейты требуют расширения runtime mutation boundary и UI Orca, которого нет в текущем plugin API. Протокол, evidence и ограничения: [программный workflow поверх Orca](plans/2026/2026-10-11-orca-programmatic-flow-research/research.md).

## Graphify и OmniRoute

Бандл Graphify поставляет полный upstream-скилл версии 0.9.82 с рамкой ADC и references, закреплённый Python-пакет `graphifyy` с CLI `graphify`, правила использования графа и stdio MCP ADC. Последний вызывает публичные query/explain/path/affected CLI с фиксированным индексом checkout. Каждый worktree имеет собственный индекс. Свежесть определяется по хешам Git-visible файлов и версии тулзы; при изменении выполняется локальный `graphify update --force`, без вызовов моделей. Состояние индекса сохраняется только после успешного построения.

После доставки и освобождения её общего lock синхронизация запускает отдельный фоновый процесс `adc graphify-refresh`. Это относится к запуску workspace, подготовке worktree и адаптерам агентов: вызывающая команда не ждёт даже проверки свежести графа. Индексация не задерживает Orca, запуск агента или публикацию ready. Фоновый процесс пишет вывод и ошибки в `<checkout>/.adc/graphify.log` и использует отдельный lock checkout в `ADC_HOME/locks/graphify-<checkout-id>`. Если lock занят, повторный фоновый процесс завершается без ожидания и очереди. Команды `adc tools graphify` и инструменты MCP используют тот же lock; явная команда `adc tools graphify index` и вызовы инструментов MCP дожидаются проверки и обновления индекса. Другие проекты и изменения capabilities/skills/MCP могут получать общий lock, пока индекс строится. Ошибка автоиндекса остаётся в журнале и не отмечает граф актуальным; MCP возвращает isError с рекомендацией использовать исходники. Бандл не устанавливает глобальные agent plugins или Git hooks. Самостоятельное обновление скилла тулзой отключено через GRAPHIFY_NO_AUTO_REFRESH, чтобы сохранить read-only слой и проектные форки.

OmniRoute 3.8.51 устанавливается в том инструментов из npm с явным allowlist lifecycle scripts; пин находится в runtime/tools-lock.json. `adc omniroute serve` запускает панель без открытия браузера внутри контейнера. DATA_DIR указывает на сохраняемый ~/.omniroute, cwd установлен в home, чтобы проектная .env не управляла общим шлюзом. Провайдеры и агенты настраиваются пользователем; ADC не выполняет авторизацию и запросы к моделям при установке.

Архивы Claude создаются и восстанавливаются Go-командой `adc tools claude-snapshot`: транскрипты не перезаписываются при восстановлении, пути и типы записей проверяются. `adc tools pnpm-patch-dep` сохраняет manifest, workspace YAML и lockfile до установки и возвращает их при ошибке. Версии pnpm до 11 используют package.json overrides, новые — pnpm-workspace.yaml.

Claude устанавливается официальным npm-пакетом @anthropic-ai/claude-code в общий том инструментов. Optional dependency содержит нативный бинарник, postinstall этого пакета явно разрешён. Рабочая существующая установка сохраняется; при восстановлении заменяются только неисправные launchers и проверяется --version. Настройки, авторизации и истории не удаляются. Такой путь не использует скачивание через curl из shell-установщика Claude.

Загрузки инструментов и установочные команды повторяются при временных DNS/transport ошибках и HTTP 408/429/500/502/503/504: до пяти попыток с паузами 1/2/4/8 секунд. Оборванные HTTP bodies скачиваются заново; неполные данные не выполняются. Внешние команды повторяются только при распознанной сетевой ошибке в выводе. Исключение — официальный установщик OpenCode: его тихий curl-запрос метаданных может завершиться с кодом 6 без вывода, такой DNS-сбой тоже повторяется; для остальных команд голый код 6 не считается сетевой ошибкой. Ошибки доступа, HTTP 404 и неверные сертификаты не повторяются. Git установщиков получает GIT_HTTP_LOW_SPEED_LIMIT=1 и GIT_HTTP_LOW_SPEED_TIME=30: HTTP-передача со скоростью менее 1 байта/с в течение 30 секунд завершается retryable ошибкой Operation too slow; HTTP/2 curl 92 тоже распознаётся как временный сбой. Это ограничение отсутствия сетевого прогресса, не общей длительности clone. Интерактивные запросы Git отключены только в окружении установщиков. npm и uv дополнительно получают штатные настройки повторов запросов; браузерная установка использует тот же исполнитель. Проверки --version не повторяются как установка.

Runtime публикует этапы подготовки и итог ready/failed в атомарном /tmp/adc-startup.json. Право публиковать эти этапы задаётся внутри процесса подготовки; унаследованная переменная ADC_STARTUP_STATUS его не включает. Последующие sync, setup worktree, адаптеры агентов и фоновая индексация не перезаписывают ready. Workspace start показывает этап, номер попытки установки и напоминание каждые 15 секунд, затем возвращает консоль. Контейнер работает в фоне; Ctrl+C прекращает только ожидание. Прежний предел ожидания 10 минут сохраняется: при его истечении сообщается о продолжающейся фоновой подготовке. Workspace status отличает running (готов) от running (подготовка: этап). Этап от предыдущего запуска отбрасывается по сравнению Updated с Docker StartedAt; логи Orca и pairing не копируются в файл статуса и промежуточный вывод прогресса.

После подтверждения ready хостовая команда workspace start читает Docker logs текущего запуска контейнера через --since Docker StartedAt и выводит pairing.url последнего события orca_server_ready в строке Access link. Ссылка из предыдущего запуска не используется. Ошибка чтения или отсутствие доступного pairing URL не отменяют готовность: команда предлагает найти ссылку через adc workspace logs. По умолчанию workspace logs показывает полный журнал контейнера; --tail N ограничивает число строк, --tail all явно выбирает полный журнал, --follow/-f продолжает вывод новых сообщений.

adc doctor project <path|id> выполняет только чтение: проверяет Git root, регистрацию, старые каталоги, контракт ADC, возможности проекта и ссылки в местах доставки. Host help и completion содержат хостовые и перенаправляемые команды; runtime help скрывает управление установкой и Docker, сохраняя project list и workspace map. Версия бинарника содержит 12 символов VCS revision и dirty для сборки с локальными изменениями; Docker получает ту же ревизию через build arg. Без метаданных выводится unknown.

На хосте doctor project разрешает относительные цепочки симлинков и сопоставляет контейнерные пути текущего checkout с хостовым каталогом. Ссылки на недоступные здесь контейнерные хранилища отмечаются одним счётчиком для проверки внутри ADC; отсутствующие цели в сопоставленном checkout и циклы остаются ошибками. В runtime проверяются настоящие цели. Подробности каждой ошибки выводятся один раз.

## Миграция с v0

adc migrate legacy import-host читает прежний план и копирует только примонтированные профили и три файла общего store: share/mcp/servers.json, share/mcp/secrets.env, share/hermes/auth.json. Репозитории регистрируются по исходным host path, кеши, DinD и writable layers не архивируются. Проверенная копия профилей сохраняется в ~/.adc/backups/profiles; manifest scope mounted-profiles отличает её от полного backup. Старые полные backup/import остаются доступны.

ADC хранит служебное состояние checkout в .adc: MCP ownership, базы форков, checkpoint Graphify и копии конфигов. На первом sync прежний .ai-devcontainer копируется через staging с проверкой SHA-256; оригинал сохраняется до явного cleanup. Независимо созданные два каталога не объединяются автоматически. Cleanup сохраняет новое состояние .adc.

Защита обновления от работающих контейнеров приводит к абсолютному пути и разрешает симлинки как в пути платформы, так и в источнике bind-маунта. Это учитывает алиасы macOS /var и /private/var и ссылки на каталог платформы; ошибка разрешения пути платформы останавливает обновление.

Полный архивный путь adc migrate legacy plan/backup/verify/import/finish реализован на Go. План строится по явно выбранным devcontainer и содержит постоянные маунты с уникальными идентификаторами ресурсов. Родительский .ai-devcontainer-dev включается целиком ради файла projects и неактивных профилей. Порядок маунтов Docker не влияет на план. Backup требует остановленных контейнеров, проверяет других Docker-писателей и сохраняет bind-маунты, тома, docker export и полный docker inspect в частные файлы. Маркер backup.json появляется после копирования и повторной проверки контейнеров; SHA-256 и размеры проверяются перед импортом.

Импорт выполняется только в отдельный пустой workspace и новые тома. Выбранный --account определяет общие аккаунты и настройки; исходные данные каждого профиля сохраняются отдельно в ~/.adc-legacy/<project>/home. Обычные session files Claude/Codex объединяются без перезаписи конфликтующих файлов, текстовая история дополняется, SQLite-базы не объединяются. Известная ссылка авторизации Hermes разрешается через снимок общего тома. Каталоги Obsidian и данные OpenCode из writable layer также копируются. Исходные каталоги и тома подключаются только read-only при резервном копировании; импорт читает только immutable backup и пишет в новые тома. Старые контейнеры, платформенный клон и checkout не изменяются импортом.

Импорт публикуется из private staging и получает завершающий отчёт с fingerprint исходного backup. Host journal migration-pending.json блокирует workspace start до подтверждения копии. Команда finish завершает регистрацию после прерывания между копированием и сохранением реестра. Частично опубликованные тома автоматически не удаляются и не активируются. DinD, сторонние сервисы, настройки портов и расширения VS Code остаются в backup и требуют отдельного запуска. Руководство: [переход со старых devcontainer](docs/migration.md).

После проверки новой среды adc migrate legacy cleanup <project|path> показывает доставленные документы, скиллы, MCP-конфиг и служебное состояние, которые можно сбросить перед новой синхронизацией. Без --apply это предпросмотр без записи; --devcontainer явно включает весь проектный .devcontainer. Применение требует остановленных Docker-контейнеров с маунтом проекта, копирует выбранные файлы и ссылки в ADC_HOME/backups/project-cleanup, сверяет SHA-256 и повторно проверяет источники перед удалением. Копия получает cleanup.json с исходными контрольными суммами и статусом. Путь проекта и путь backup раскрывают симлинки перед проверкой пересечения: backup внутри проекта запрещён также через алиасы macOS /var и /private/var. Родительские симлинки не обходятся, внешние цели ссылок не копируются и не удаляются. Проектные AGENTS.md/CLAUDE.md, .agents конфиги и форки, непомеченные скиллы и настройки агентов остаются у проекта. После очистки запуск workspace или поддерживаемого агента восстанавливает доставку выбранных возможностей.

Переход установки использует стандартные ~/.local/share/ai-devcontainer и ~/.adc. Bootstrap отдельно компилирует новый Go helper, который отказывается менять грязный клон или платформу с работающими контейнерами, копирует её вместе с .git в ADC_HOME/backups/platform-v0 и сравнивает полный SHA-256 дерева. После проверки и повторного контроля контейнеров он переключает обычный клон на main без сброса локальных коммитов main. Старый симлинк команды заменяется исполняемым файлом, даже если bin/adc теперь стал каталогом Go-кода. Авторизации, истории, рабочие репозитории и тома этот шаг не изменяет. Исправленный updater ветки v0 поддерживает adc update --branch main и передаёт управление bootstrap без предварительного pull нового дерева. Для получения этого исправления старым CLI нужен одноразовый Git fetch/switch. Опциональный --no-shell сохраняет прежние PATH и профили оболочек, но для обычного перехода не требуется.

## Проверки и разработка

```sh
gofmt -w bin/adc
go vet ./...
go test -race ./...
go build -o .build/adc ./bin/adc
ADC_TOOL_BUNDLES_INTEGRATION=1 ADC_INTEGRATION=1 go test -v -count=1 -timeout=35m ./bin/adc/integration
```

CI запускает нативные Go-тесты на Linux, macOS и Windows и компилирует шесть сочетаний ОС и архитектуры. Go tests проверяют CLI, установщик, каталог и доставку, изоляцию конфигураций checkout, секреты и сохранение setup-команд Orca. Go Docker smoke проверяет Orca, два репозитория, создание worktree, PTY с баннером, окружение оболочек и сохранение данных, истории и пользовательского профиля. Дополнительный режим ADC_TOOL_BUNDLES_INTEGRATION проверяет установку Graphify/OmniRoute, обновление dirty checkout, все четыре реальных MCP-инструмента, отдельный граф worktree, локальную панель и сохранение ключа шифрования шлюза. Назначение наборов описано в [tests/README.md](tests/README.md).

Тесты ремонта старых ссылок DSH и README используют абсолютные пути с диском на Windows; на Linux и macOS сохраняются проверки прежних контейнерных путей /workspaces и /opt/dev-platform. Во всех вариантах проверяются повторная доставка и сохранение чужих ссылок и пользовательских скиллов.

План изменения: [общая рабочая среда разработчика](plans/2026/2026-10-09-developer-workspace/task.md).

При переходе со старой доставки README.md не рассматривается как каталог скилла; оборванные проектные ссылки на скиллы пропускаются с предупреждением. Документные ссылки на известные прежние пути ADC (docs/skills-README.md, docs/plans-README.md, docs/MONOREPO.md и их прежние варианты delivery/documents) обновляются на текущие источники. Чужие документы и ссылки вне известных корней платформы сохраняются. Непомеченный каталог в .claude/skills при совпадении имени с платформой остаётся пользовательским: доставка не изменяет его и отмечает конфликт источников в AGENTS.skills.md.

Ошибки синхронизации отдельных проектов публикуются как failed и возвращаются хостовой команде start, но сервер Orca продолжает работать без автоматического рестарта runtime. Регистрация репозиториев в Orca выполняется также после ошибок проектной доставки. Готовность всей среды не объявляется и adc-ready не создаётся, пока синхронизация не завершена успешно. После исправления проектов adc workspace start повторяет неудачную подготовку и проверяет готовность. Общие ошибки установки, карты workspace и сервера Orca остаются фатальными.

Docker smoke доставки проверяет обновление с хоста и из runtime, два проекта и worktree, управляемые документы, сохранение форков и read-only файлов, неизменность контейнера и бинарников. Та же тестовая платформа проходит обычный Go-тест с полной доставкой в новый проект: он выявляет пропущенные источники, включая шаблон MCP-секретов, до сборки образа. В CI Docker smoke запускается с -failfast, чтобы после первого падения причина оставалась в конце лога. В прогоне b32c907 этот тест упал из-за отсутствующего шаблона, остальные Docker-тесты прошли; повторный Docker-прогон после исправления ещё не выполнен, поскольку в текущей среде нет команды docker.
