# Установка и использование

Проверенный установщик — skills 1.7.2; ему нужен Node.js >=22.20.0. Приёмка выполнена на Node.js 24.20.0; Node.js 20.19.0 завершает запуск ошибкой отсутствующего fs/promises.glob. Выберите уже установленный совместимый Node.js перед командой.

Установка из локального checkout ADC, содержащего эту версию:

```sh
npx --yes skills@1.7.2 add <adc-checkout>/delivery/skills/foxford-frontend-review --agent claude-code codex --copy --yes
```

Выполняйте команду из нужного проекта. Для изолированной проверки сначала создайте временный пустой каталог и перейдите в него. `--copy` доставляет соседние CODESTYLE.md, USAGE.md и meta.json вместе с SKILL.md, без зависимости от исходного checkout. Установку проверяйте через `npx --yes skills@1.7.2 list --json`, наличие файлов и доступность относительных ссылок. Глобальная установка здесь не требуется.

После публикации ветки с этим skill в командном репозитории:

```sh
npx --yes skills@1.7.2 add foxford/ai-devcontainer --skill foxford-frontend-review --agent claude-code codex --copy --yes
```

Команда без ref использует опубликованную ветку по умолчанию. Для другой опубликованной ветки укажите URL `https://github.com/foxford/ai-devcontainer/tree/<branch>/delivery/skills/foxford-frontend-review`. До публикации проверяется локальная установка; она не доказывает доступность неопубликованной версии через GitHub.

Примеры явного обращения к установленному skill:

```text
$foxford-frontend-review Проверь и исправь изменения тикета от <base-sha>, включая staged, unstaged и новый client/Card.css. user-notes.css — отдельная пользовательская работа.

$foxford-frontend-review Без изменений: проверь frontend-часть PR от <base-sha> и рабочий результат. Верни замечания со ссылками на правила.
```

В Claude Code используйте `/foxford-frontend-review` с тем же поручением. После установки откройте новую сессию, если агент ещё не обновил каталог skills. Из другого workflow передавайте базу, состав задачи и режим; установщик не подключает skill к implement автоматически.

## Будущее подключение к обычному implement

Точка вызова — после code-review и до коммита конкретного implementation-тикета. Установка только копирует поставку: для автоматического вызова потребуется отдельная правка workflow. Универсальная интеграция со стандартными review не гарантируется; существующие implement, code-review и runner этой поставкой не меняются.

Передайте вызову один контракт области:

```text
$foxford-frontend-review
Режим: исправление.
Тикет: <путь или текст>.
База: <проверенный SHA>; HEAD: <SHA проверяемой версии>.
Релевантные коммиты: <список>.
Рабочий результат: <staged/unstaged файлы и участки>; новые файлы: <список>.
Чужая работа: <файлы и участки, которые сохранить>.
Проектные инструкции и команды проверок: <источники>.
```

После результата владелец implement читает оставшиеся замечания и фактические результаты проверок. При неполной проверке, неуспешной проверке или запросе решения зависимая часть остаётся незавершённой. Запрос решения по макету сам по себе не означает принятого отклонения. Runner не распознаёт его автоматически: будущая интеграция должна явно передавать ожидание решения человеку и останавливать зависимую работу.

Если проверки выполняются параллельно, заранее зафиксируйте для всех одну анализируемую версию: base/HEAD плюс снимок staged, unstaged и новых файлов. Один HEAD недостаточен для незакоммиченного результата. Все проверяющие работают без записи; дождитесь их завершения. Затем один назначенный владелец исправляет результат, проверяет защиту чужих изменений и повторяет затронутые проверки. Если версия изменилась во время review, замечания нужно сверить с новым снимком; коммит выполняется по отдельному поручению.
