# Поставка рабочей среды ADC

ADC подключает существующие репозитории к общей среде через `adc project add`. Команда `adc workspace start` запускает среду, `adc sync` доставляет инструкции и выбранные возможности.

- [Назначение, быстрый старт и команды](../README.md).
- [Установка и обновление](installation.md).
- [Настройки проектов, MCP, знания и миграция](workspace.md).
- [Архитектура платформы](../SPEC.md).

При переходе с проектных devcontainer проверьте новую среду и при необходимости импортируйте авторизации с резервной копией. ADC не удаляет прежние devcontainer-файлы из подключённых репозиториев.

## Версии единиц доставки

У каждого скилла и бандла есть `meta.json` в его каталоге. У каждого MCP есть `<имя>.meta.json` рядом с файлом его определения: общим `delivery/mcp/servers.json` или `mcp.json` внутри бандла. Все метафайлы имеют один формат:

```json
{
  "kind": "skill",
  "name": "humanizer",
  "version": "3.31.4-adc.1"
}
```

`kind` принимает `skill`, `mcp` или `bundle`; пара `kind/name` уникальна в поставке. `version` обозначает выпуск содержимого по SemVer. Поле `version: 1` в существующем `bundle.json` остаётся версией формата и не участвует в сравнении обновлений.

При изменении единицы повысьте её версию в метафайле. Для изменённого скилла или MCP внутри бандла повысьте также версию бандла. Локальные исправления импортированного скилла можно обозначать последовательными версиями `3.31.4-adc.1`, `3.31.4-adc.2`. Изменение содержимого без изменения версии не создаёт уведомление. Отдельного списка версий и снимков содержимого нет.

После публикации ADC получает эти метафайлы из tracking-ветки платформы. Более высокая версия или новая единица появляется в `adc updates`; равная и более старая версия не предлагаются. Применение выполняется обычной командой `adc update`. Проектные форки сохраняют свои правила приоритета; наличие новой платформенной версии не означает автоматическую замену форка.
