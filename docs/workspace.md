# Работа с проектами в ADC

[README](../README.md) описывает быстрый старт и основные команды. Здесь собраны настройки знаний, возможностей, MCP и скиллов, а также правила хранения данных и миграции.

## Проекты и знания

Каждый агент получает ссылку на `/workspace/AGENTS.workspace.md`. В ней перечислены все подключённые проекты, их назначение, права доступа, связи и источники знаний с происхождением и датой регистрации. Агент выбирает источники по задаче, затем читает инструкции затронутых репозиториев.

Связь проектов и документ можно зарегистрировать так:

```sh
adc project relate frontend backend
adc project knowledge frontend docs/architecture.md 'Команда frontend'
adc workspace map
```

`relate` записывает направленную связь в реестр и сообщает, какие проекты связаны. `workspace map` обновляет инструкции среды и выводит путь `/workspace/AGENTS.workspace.md`; прочитать карту можно в терминале ADC или Orca командой `cat /workspace/AGENTS.workspace.md`.

Проект с флагом `--readonly` доступен для чтения; ADC не изменяет его файлы при доставке. Это позволяет подключить документацию или соседний репозиторий как источник знаний.

Общий источник регистрируется по абсолютному пути внутри среды и должен находиться в подключённом проекте:

```sh
adc project knowledge global /absolute/runtime/path/docs/domain.md 'Команда платформы'
```

## Возможности и проектные настройки

Возможности выбираются при регистрации через `adc project add <path> --capability <names>`. Их состав и команды перечислены в [README](../README.md#возможности-для-проекта).

Для уже подключённого проекта выполните из его каталога `adc project capability list`: команда показывает полный каталог с описаниями и MCP, а зелёная `✓` отмечает эффективный выбор текущего checkout. В выводе, перенаправленном в файл, и при `NO_COLOR` галочки остаются без ANSI-цвета. Галочка обозначает выбранную возможность, а не проверку её инструментов или соединений MCP. Вне подключённого проекта выводится каталог без выбранных возможностей.

`adc project capability add graphify` добавляет возможность, `adc project capability add frontend figma` — несколько сразу. Команды сохраняют остальные поля `.agents/project.json`, проверяют неизвестные имена и несовместимости до записи, затем автоматически синхронизируют текущий checkout. Повторное добавление не создаёт дубликатов. Работают на хосте и внутри ADC, включая worktree; read-only проекты отклоняются. Если workspace остановлен или доставка не удалась, настройки остаются сохранены: запустите среду либо исправьте ошибку и повторите команду добавления или удаления.

`adc project capability rm figma` убирает возможность из командного файла и синхронизирует доставку. Возможность, выбранная локально при регистрации через `--capability`, остаётся частью эффективного выбора; для её удаления измените `capabilities` в `~/.adc/workspace.json` при остановленной среде. Команда `rm` объясняет этот случай и не делает частичную правку.

Для общего выбора команды создайте `.agents/project.json` в репозитории:

```json
{
  "capabilities": ["pnpm-nx", "changesets", "playwright"]
}
```

Сохраните файл в Git, чтобы другие разработчики получили тот же выбор. Команды `adc project capability add` и `adc project capability rm` применяют изменения сразу; ручные правки файла подхватываются при следующем запуске поддерживаемого агента или workspace. Локальные возможности из регистрации дополняют командные. Локальный выбор хранится в `~/.adc/workspace.json`; редактируйте его при остановленной среде.

Состав доставки задаёт [delivery/catalog.json](../delivery/catalog.json). Базовый слой описан полями `base.instructions`, `base.documents`, `base.skills` и `base.mcp`; дополнения описаны в `capabilities.<имя>.instructions/documents/mcp`. Все пути источников относятся к `delivery/`: инструкции, документы, скиллы и MCP используют одно правило. Автодополнение читает этот же каталог.

Одна возможность может доставлять несколько MCP: `frontend` включает Playwright и Chrome DevTools. ADC убирает повторяющиеся инструкции и серверы. Поле `conflicts` задаёт несовместимость возможностей; конфликт командного и локального выбора также приводит к ошибке.

Выбор возможностей доставляет инструкции и конфигурацию агентам. Стек, зависимости приложения и команды проверки определяются самим репозиторием.

## Obsidian

Запустите Obsidian, откройте нужный vault, установите и включите плагин [Local REST API](https://github.com/coddingtonbear/obsidian-local-rest-api). Для обычного HTTP включите **Enable HTTP server**: штатный порт `27123`, путь MCP `/mcp/`. API key находится в настройках этого плагина. Установку Obsidian, плагина и сетевой доступ на хосте настраивает пользователь.

Из терминала зарегистрированного проекта выполните `adc project capability add obsidian`. Команда показывает требования из `delivery/bundles/obsidian/bundle.json` и задаёт два вопроса:

| Вопрос | Что вводить |
|---|---|
| Адрес MCP Obsidian | Полный HTTP/HTTPS URL `/mcp/`, доступный из ADC runtime; предложенный адрес `http://host.docker.internal:27123/mcp/` |
| API key Obsidian Local REST API | Ключ из настроек плагина; ввод скрыт |

`host.docker.internal` — предложенный адрес, его доступность зависит от размещения Docker и Obsidian. В WSL2 Obsidian может работать в Windows, а Docker — в другом окружении; для соединения могут потребоваться адрес Windows, разрешение firewall и настройка адреса прослушивания плагина. `localhost` в URL внутри ADC означает сам контейнер. Для HTTPS нужен доверенный контейнеру сертификат; ADC не отключает проверку TLS.

Если WSL использует mirrored networking, а Obsidian или Chrome слушает Windows localhost, настройте [мост с автозапуском для Windows-сервисов](wsl-host-services.md). В справочнике показаны Obsidian `/mcp/` и подключение Chrome DevTools MCP к уже запущенному Windows Chrome через CDP.

Адрес сохраняется в `.agents/mcp.local.json`, ключ — в `.agents/mcp.secrets.env` с правами `0600`; оба файла исключаются из Git. `.agents/project.json` хранит только выбор возможности и может коммититься. Повторное добавление использует сохранённые адрес и ключ без вопросов, но снова проверяет подключение. Чтобы изменить их, выполните `adc mcp doctor obsidian --fix`: Enter оставляет показанный адрес или сохранённый скрытый ключ.

Проверка выполняет `initialize`, `notifications/initialized` и `tools/list` с авторизацией; инструменты не вызываются и заметки не изменяются. Только после успешной проверки `capability add` продолжает штатную доставку. При сетевой ошибке, неправильном ключе или ошибке MCP команда завершается с ненулевым кодом: настройки остаются для исправления, успешная активация не объявляется. Неинтерактивный запуск с отсутствующими параметрами завершается с объяснением; `adc workspace start` и `adc update --delivery` не запрашивают настройки MCP.

## Драйверы агентов

Claude, Codex и OpenCode получают один состав возможностей через отдельные драйверы с общим интерфейсом подготовки конфигурации и запуска. Hermes и DSH также подключены через этот интерфейс. Доставка инструкций и скиллов общая; драйверы переводят MCP в родной формат агента. Новый агент требует собственного драйвера, поскольку формат его конфигурации и правила запуска могут отличаться.

Claude получает управляемый `.mcp.json`. Если файл принадлежит пользователю, он сохраняется, а ADC передаёт дополнительный приватный `.adc/claude-mcp.json` через `--mcp-config` при запуске сессии адаптером. Codex получает записи с namespace checkout в своём `config.toml`: HTTP-заголовки записываются автоматически с правами `0600`, без секретов в аргументах CLI. ADC обновляет только созданные им блоки заголовков и сохраняет существующие ручные блоки. OAuth по-прежнему авторизуется в самом агенте.

OpenCode получает приватный `.adc/opencode.json` для текущего checkout с MCP и дополнительными инструкциями. Адаптер ADC передаёт его через `OPENCODE_CONFIG_CONTENT` при запуске из проекта; глобальный и проектный JSON/JSONC пользователя не изменяются. Существующий пользовательский inline-конфиг сохраняет приоритет конфликтующих ключей. В конфиг другого checkout серверы проекта не попадают. Запуск CLI напрямую в обход адаптера ADC не добавляет этот слой.

После изменения MCP начните новую сессию выбранного агента в Orca. Проверка транспорта ADC не проверяет аккаунт модели и не подтверждает выполнение задачи агентом.

## MCP и секреты

По умолчанию базовый слой не выбирает MCP. Каталог выбирает имена серверов, а [delivery/mcp/servers.json](../delivery/mcp/servers.json) хранит определения, закреплённые версии и условия `x-requires`. Сервер без требуемого браузера или секрета не доставляется. Как включить готовые серверы, описано в [README](../README.md#включить-и-проверить-mcp).

`adc mcp doctor` проверяет все включённые MCP текущего checkout; `adc mcp doctor <имя>` — один сервер. HTTP использует Streamable HTTP с JSON/SSE ответами, stdio запускает отдельный процесс с окружением и рабочим каталогом сервера. На сервер отводится до 20 секунд; проверяются авторизация, согласование сессии и все страницы `tools/list`. Не вызываются `tools/call`; ошибки сервера и тела HTTP не печатаются вместе с возможными секретами. Отключённые серверы отмечаются отдельно; неизвестное имя и неисправный выбранный сервер возвращают ошибку.

`adc mcp doctor <имя> --fix` запрашивает параметры из `activation` выбранного бандла либо недостающий секрет из `x-requires`, сохраняет их, доставляет конфигурацию и повторяет проверку. Пути к отсутствующим инструментам, OAuth, установку плагинов и проблемы сети он объясняет; автоматически исправить их вводом ключа нельзя. Вопросы и сетевые проверки выполняются без общего lock; запись и доставка конфигов — под lock.

Команды MCP выполняйте из каталога подключённого проекта. Чтобы добавить свой сервер, используйте `adc mcp add`; точные флаги доступны через `adc mcp --help`.

| Слой | Для кого | Файл | Флаг команды |
|---|---|---|---|
| Платформенный | Готовые серверы из выбранных возможностей | `delivery/mcp/servers.json` платформы | Управляется платформой |
| Пользовательский | Мои серверы во всех проектах | `/opt/ai-tools/share/mcp/servers.json` | `--user` |
| Проектный | Серверы команды, хранится в Git | `<repo>/.agents/mcp.json` | `--project` |
| Локальный | Мои серверы только в этом проекте | `<repo>/.agents/mcp.local.json` | `--local` |

Проектные слои перекрывают глобальные, личные перекрывают общие. Слияние рекурсивное: можно изменить одно поле сервера, сохранив остальные. Значение `null` выключает сервер из нижнего слоя. Пользовательские, проектные и локальные слои могут добавлять серверы, которых нет в каталоге платформы.

Секреты проекта хранятся в `.agents/mcp.secrets.env`, общие секреты разработчика в `/opt/ai-tools/share/mcp/secrets.env` внутри среды. В конфигурации используйте `${ИМЯ}`. Команда `adc mcp enable <имя> --project` запрашивает недостающий секрет без отображения ввода и записывает его локально. Без явного флага `enable` использует пользовательский слой.

В общих конфигурациях агентов имена MCP включают ID проекта и checkout. Токены каждого проекта берутся из его секретов; синхронизация одного checkout сохраняет конфигурацию соседних. Записи ADC защищены общей системной блокировкой.

## Скиллы и инструкции

ADC собирает скиллы из платформы и `.agents/skills` проекта. Проектный вариант перекрывает платформенный. Команды `adc skill fork`, `adc skill status` и `adc skill unfork` позволяют изменить отдельные файлы скилла и отслеживать изменения платформы.

`adc updates` показывает опубликованные версии скиллов, документов, инструкций, MCP и бандлов, которые новее локальных, и ничего не применяет. Команда `adc update --delivery` скачивает доставку без пересборки образа и перезапуска среды. В работающей среде доставка применяется к подключённым проектам и их worktree сразу; в остановленной — при следующем запуске. Read-only проекты не изменяются. Чтобы агент прочитал новые инструкции, скиллы и MCP, откройте новую сессию после обновления. Правила метафайлов описаны в [справочнике доставки](devcontainer-delivery.md#версии-единиц-доставки).

Скилл `humanizer` редактирует русские тексты и включает полный Python-сканер humanizer-ru со справочниками. Его закреплённые зависимости подготавливает изолированный `uv run` по `requirements.txt` скилла, без изменения окружения приложения. При первом запуске нужны доступ к пакетному реестру и разрешение зависимостей по правилам проекта; последующие запуски используют кеш uv. Инструкции запуска и ограничения измерений находятся в самом скилле.

Общие скиллы в домашнем каталоге агента остаются платформенными. Проектные варианты получают отдельные имена для каждого checkout. Правила и команды описаны в [справочнике скиллов](../delivery/documents/skills/README.md).

Доставка сохраняет ручной текст `AGENTS.md` и `CLAUDE.md`, добавляет управляемые блоки, создаёт `AGENTS.platform.md`, индекс скиллов и правила игнорирования служебных файлов. Обновление документов касается файлов и блоков ADC; остальные README, спецификации и документы проекта команда не переписывает.

## Orca, агенты и worktree

Приложение Orca работает на компьютере разработчика и подключается к серверу внутри Docker. Новые workspace ADC по умолчанию публикуют сервер на `127.0.0.1:6770`, отдельно от стандартного порта `6768` десктопной Orca. Ранее созданные workspace сохраняют свой порт. Команда `adc workspace config` показывает сохранённые порты; `adc workspace config --port 6770` меняет порт Orca для следующего `adc workspace start`. Команда `workspace init` создаёт только новую конфигурацию и не меняет существующую.

После подготовки `adc workspace start` показывает адрес сервера и актуальный pairing URL в строке `Access link`. Если ссылку получить не удалось, команда предлагает открыть `adc workspace logs` и найти `pairing.url` в последнем событии `orca_server_ready`. Pairing URL даёт доступ к серверу; не публикуйте его. Для управления сервером через CLI используйте `adc orca ...`.

`adc workspace logs` по умолчанию показывает полный журнал контейнера, включая события запуска Orca. Можно ограничить число строк или следить за новыми сообщениями:

```sh
adc workspace logs --tail 100    # последние 100 строк
adc workspace logs --tail all    # полный журнал, как без флагов
adc workspace logs --follow      # полный журнал и новые сообщения; сокращённо -f
```

Пошаговое подключение клиента, выбор агента и постановка задачи через интерфейс описаны в [README](../README.md#настроить-orca). Для локального Docker/WSL клиент Orca может блокировать loopback URL до включения **Advanced → I am using an SSH tunnel to this local address**; этот переключатель разрешает уже существующий локальный проброс порта. **Run on → ADC Developer** направляет запуск в контейнер; настройка **Agent runtime: Windows / WSL** относится к локальным проектам.

Команда `adc worktree create <project> <name>` создаёт worktree средствами Orca и доставляет контекст перед завершением. Claude Code, Codex, OpenCode, Hermes и DSH также получают контекст перед запуском своего CLI через адаптер ADC. Индексация Graphify выполняется в фоне и не задерживает setup worktree или запуск агента. Это работает даже без закоммиченного `orca.yaml`.

Для дополнительных агентов используйте setup hook из `orca.yaml`. ADC сохраняет прежние setup-команды и оригинал файла в `.adc/backups`. При записи YAML значения сохраняются, но комментарии и форматирование могут измениться; проверьте эту правку при подключении проекта.

### Диагностика подключения Orca

Если `adc workspace start` завершается ошибкой Docker `port is already allocated` или `address already in use`, хостовый порт уже занят. Десктопная Orca запускает локальный сервер с портом по умолчанию `6768`; если она заняла этот порт первой, Docker не сможет опубликовать на нём ADC. Это возможно на macOS и других ОС. Поведение подтверждается [исходниками Orca v1.4.223](https://github.com/stablyai/orca/blob/v1.4.223/src/main/startup/main-process-runtime-launch.ts#L60-L93). Переключатель **I am using an SSH tunnel to this local address** разрешает подключение клиента к loopback, но не освобождает порт.

На macOS процесс, слушающий старый порт ADC, можно проверить в терминале:

```sh
lsof -nP -iTCP:6768 -sTCP:LISTEN
```

Замените `6768`, если workspace использует другой порт. Выберите для ADC свободный порт и сохраните его в существующей конфигурации:

```sh
adc workspace config --port 6770
adc workspace start
```

Если `6770` тоже занят, укажите другой свободный порт. Проекты и данные сохранятся. При смене порта следующий `start` пересоздаст контейнер и завершит его активные сеансы, поэтому сначала завершите работу агентов. Подключите Orca по новой строке `Access link` из вывода `start`. Если ADC сообщает о незавершённом переключении контейнера, сначала освободите прежний порт и выполните `adc workspace start` для завершения восстановления; затем меняйте настройки.

На хосте ADC выполните `adc workspace status`, `adc orca status --json` и `adc orca repo list --json`. Готовый runtime сообщает `reachable: true`; список `repos` должен содержать подключённые проекты. Эти команды проверяют сервер изнутри ADC; доступность порта со стороны приложения проверяется отдельно.

При запуске Orca в Windows, а ADC в WSL выполните в Windows PowerShell:

```powershell
Test-NetConnection 127.0.0.1 -Port 6770
```

Ожидайте `TcpTestSucceeded: True`; при другом порте workspace замените `6770`. Открытый TCP-порт сам по себе не подтверждает, что его обслуживает ADC: это может быть десктопная Orca или другой процесс. Если порт доступен, но клиент не подключается, проверьте, что скопировали полный актуальный `pairing.url` из последнего события `orca_server_ready`, разрешили loopback в форме подключения и используете совместимые версии Orca. Сетевые ошибки, ошибку pairing и несовместимость версий клиент показывает при добавлении сервера. Для доступа с другого компьютера нужен отдельный маршрут и достижимый адрес; штатная публикация ADC привязана к loopback текущего хоста.

Orca в образе обновляется через ADC, поэтому клиент может показывать **Manual update**. Завершите работу агентов, затем выполните на хосте `adc update`: работающий workspace автоматически перезапустится после обновления, команда покажет этапы подготовки и дождётся готовности. Если workspace был остановлен, запустите его отдельно через `adc workspace start`. Данные среды остаются в постоянных томах.

### Перенести результат worktree в main

В worktree задачи просмотрите diff и выберите для коммита только нужные изменения через **Source Control** Orca или обычный Git. Узнайте реальное имя ветки: название workspace может отличаться от него.

```sh
git branch --show-current
```

Откройте терминал основного checkout **main** в Orca и выполните `git status --short`. Сохраните имеющиеся незакоммиченные изменения отдельным коммитом или stash перед слиянием. Следующий пример предполагает, что основной checkout уже на `main`, рабочее дерево чистое, а ветка задачи называется `check-tests`:

```sh
git merge --no-ff check-tests
```

После разрешения возможных конфликтов и проверки объединённого кода можно выполнить `git push origin main`. Для командного review опубликуйте ветку задачи и создайте PR/MR в вашем Git-сервисе вместо прямого слияния в main. Worktree использует тот же Git-репозиторий: файлы вручную копировать не требуется. Если задача состояла только в проверках и агент не менял код, переносить в main нечего.

## Подсказки в терминале

При открытии интерактивного терминала Bash или Zsh среда показывает баннер с именем workspace и основными командами ADC. История команд сохраняется между пересозданиями контейнера.

Чтобы добавить подсказки для проекта, создайте `.agents/motd.sh` в корне репозитория:

```sh
#!/bin/sh
printf '%s\n' \
  '  Разработка   pnpm dev' \
  '  Проверки     pnpm lint && pnpm test' \
  '  Релиз        pnpm changeset'
```

Замените команды на принятые в вашем проекте и сохраните файл в Git, чтобы подсказки получили остальные разработчики и новые worktree. ADC запускает файл через `sh`, поэтому право на исполнение не требуется. Используйте синтаксис POSIX sh.

Файл дополняет общий баннер и выполняется из текущего каталога терминала. ADC находит ближайший корень Git, даже если терминал открыт в подкаталоге или worktree. Оставляйте здесь только быстрый вывод подсказок: скрипт запускается при каждом открытии терминала. Изменения видны в следующем терминале без дополнительных команд и пересборки образа.

## Хранение данных

`~/.adc/workspace.json` содержит реестр на хосте. Домашний каталог, AI-инструменты и рабочая область сохраняются в отдельных Docker volumes. Исходники подключаются явными bind-маунтами, платформа доступна только для чтения. Домашний каталог хоста и Docker socket не монтируются.

Диалоги и настройки агентов находятся в volume `adc-<имя>-home`, доступном внутри контейнера как `/home/node`: Codex — `.codex/` с sessions и SQLite-базами, Claude — `.claude/`, OpenCode — `.local/share/opencode/`, сервер Orca — `.config/orca/`. Worktrees Orca находятся в отдельном `adc-<имя>-worktrees`, подключённом к `/workspace`. Удаление контейнера сохраняет эти тома; удаление томов, сброс данных Docker или удаление WSL-дистрибутива с хранилищем Docker удаляет их. `~/.adc/backups` не является автоматической копией всех текущих диалогов. Перед полным удалением Docker сохраняйте оба тома; остановка среды перед копированием позволяет сохранить согласованные SQLite-базы.

Для sandbox Codex ADC передаёт Docker отдельный seccomp-профиль, разрешающий создание вложенного user namespace и необходимые bubblewrap операции с маунтами. Это устраняет ошибку `bwrap: No permissions to create a new namespace` при стандартном Docker seccomp. После обновления ADC нужен запуск с пересозданием контейнера; уже работающий контейнер сохраняет прежний профиль. Права Codex остаются выбранными пользователем в CLI или Orca.

Образ содержит системный `bubblewrap`, который Codex находит через PATH. Если Docker использует AppArmor, ADC загружает профиль только для своей среды: он разрешает вложенные маунты sandbox и сохраняет ограничения Docker на `/proc` и `/sys`. Для загрузки на локальном Linux-хосте нужен уже установленный `apparmor_parser`; ADC может вызвать sudo при первой загрузке или после перезагрузки хоста. Ошибка загрузки не отключает AppArmor и останавливает запуск. В WSL без AppArmor загрузка профиля не требуется.

На Unix проекты монтируются по прежним абсолютным путям, чтобы сохранить Git-ссылки существующих worktree. Сначала подключите основной checkout. На Windows основной checkout получает Linux-путь; worktree с Windows Git-путями нужно создать заново внутри ADC.

При изменении набора маунтов `adc workspace start` пересоздаёт контейнер, сохраняя данные. Остановка и пересоздание завершают живые процессы; возможность возобновить сессию зависит от агента.

## Миграция авторизаций

Для полного перехода со старых devcontainer используйте [руководство по миграции v0](migration.md): оно описывает резервную копию всех постоянных маунтов и импорт в отдельную новую среду. Команда ниже предназначена только для выбранных авторизаций.

Авторизации старой установки импортируются из явно выбранного каталога агента:

```sh
adc migrate frontend /path/to/old/project-agent-home
```

Импорт переносит только поддерживаемые файлы авторизации Codex, Claude, Hermes и DSH. Перед записью ADC сохраняет их текущие версии в резервную копию. Остальные конфигурации не импортируются в общий домашний каталог, исходная установка остаётся на месте.

Восстановление резервной копии:

```sh
adc restore /var/lib/adc/backups/<timestamp>
```

Старые devcontainer-файлы в подключённых репозиториях ADC автоматически не удаляет. После проверки новой среды их можно убрать отдельной правкой.

## Graphify: индекс и инструменты одним подключением

Подключите существующий репозиторий с `adc project add <path> --capability graphify`. Для уже подключённого проекта выполните из его каталога `adc project capability add graphify`. ADC установит CLI, доставит полный скилл с references и правила работы с графом, подключит MCP и запустит индексацию в фоне. Объявленные части поставки находятся в [бандле Graphify](../delivery/bundles/graphify/bundle.json).

Индекс хранится в `graphify-out/` конкретного checkout; у каждого worktree свой индекс. После синхронизации, подготовки worktree и перед запуском агента ADC запускает отдельный фоновый процесс, который проверяет изменения и при необходимости обновляет граф. Синхронизация, подготовка worktree, запуск агента и готовность workspace не ждут проверки или построения индекса; работа Orca от них не зависит. Одновременно индекс checkout обновляет только один процесс. Повторный фоновый запуск при занятом индексе завершается без ожидания и очереди.

Автоиндексация разбирает структуру кода локально без ключей и вызовов моделей; полный анализ документов и медиа доступен через скилл по отдельному запросу. Скилл и инструкции направляют агента сначала к графу для архитектуры и связей, затем к исходникам для проверки. Наличие инструкций не гарантирует, что любой сторонний агент будет их соблюдать.

| Действие | Команда из проекта |
|---|---|
| Обновить индекс вручную | `adc tools graphify index` |
| Задать вопрос без MCP, внутри среды | `graphify query "Как связаны модули авторизации?" --budget 1500` |
| Подписать сообщества по путям без LLM | `adc tools graphify label-paths` |
| Открыть интерактивный граф | `adc tools graphify view`, затем http://localhost:4242/graph.html |
| Восстановить установленную тулзу | `adc tools install graphify` |

MCP предоставляет graphify_query, graphify_explain, graphify_path и graphify_affected с namespace checkout. Каждый вызов этих инструментов и команда `adc tools graphify index` дожидаются проверки и обновления индекса. Прямые команды CLI работают с индексом текущего каталога: после своих изменений сначала выполните `adc tools graphify index`. Дополнительное подключение индекса руками и запуск `graphify install` не нужны. Вывод фоновой индексации, включая ошибки, сохраняется в `.adc/graphify.log` текущего checkout. Ошибка не отмечает индекс актуальным и не мешает работе с исходниками; для повторного построения используйте `adc tools graphify index`.

## OmniRoute: общий шлюз к моделям

OmniRoute поставляется внутри среды. Запустите `adc omniroute serve` и откройте http://localhost:20128. Подключите провайдеры в панели, затем укажите адрес шлюза в конфигурации нужного агента. Для CLI внутри среды используйте http://127.0.0.1:20128/v1; для host-приложений — опубликованный хостовый порт. Установка не меняет настройки провайдеров и агентов.

Данные и ключ шифрования сохраняются в `~/.omniroute` внутри тома home. Для диагностики доступны `adc omniroute --help` и `adc tools install omniroute`. Панель запускается по команде, после пересоздания среды запустите её снова. Документация продукта — [OmniRoute](https://github.com/diegosouzapw/OmniRoute).

По умолчанию Orca, OmniRoute и просмотр Graphify доступны только с этого компьютера на портах 6770, 20128 и 4242. Ранее созданные workspace сохраняют свои порты. Для изменения выполните `adc workspace config --port 6771 --omniroute-port 20129 --graph-port 4243`, затем `adc workspace start`. Можно передать только нужные флаги; остальные настройки сохранятся. Внутренние порты остаются 6768, 20128 и 4242.
