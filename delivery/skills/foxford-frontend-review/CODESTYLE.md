<a id="ff-css-001"></a>
## FF-CSS-001 — Целые пиксели для размеров и отступов

**Область:** CSS, CSS Modules, CSS-in-JS, атрибут `style` и числовые параметры, подразумевающие пиксели.

Обычные размеры и отступы задавай целыми пикселями: лишняя точность из макета затрудняет чтение и выравнивание. Сохраняй намеренные дроби и вычисления с подтверждённой причиной. Правило не округляет коэффициенты, проценты и углы и не требует раскрывать арифметические выражения.

```css
/* Было */
.card { padding: 15.999px; }

/* Стало */
.card { padding: 16px; }
```

```tsx
// Было
const Button = styled.button`width: 119.999px;`;
<div style={{ marginTop: 7.999 }} />

// Стало
const Button = styled.button`width: 120px;`;
<div style={{ marginTop: 8 }} />
```

Допустимы:

```css
/* Тонкая линия для экранов с DPR 2. */
.separator { border-bottom: 0.5px solid currentColor; }

/* Поправка на оптический центр иконки. */
.icon { transform: translateX(0.5px); }

.text { line-height: 1.5; opacity: 0.75; }
.column { width: 33.333%; transform: rotate(22.5deg); }
.layout { width: calc(100% - 16px); padding: calc(8px * 2); }
```

Необходимость оставить дробное значение устанавливай по коду, документации или проверяемому контексту; отдельный комментарий добавлять не надо. Если причина или целевое целое значение неясны, предложи уточнение. Числа в серверной логике и тексте страницы не относятся к CSS-размерам.

<a id="ff-css-002"></a>
## FF-CSS-002 — Без селекторов по тегам и сложных цепочек

**Область:** стили компонентов, включая вложенные селекторы CSS-in-JS и CSS Modules.

Оформляй элемент напрямую классом или styled-компонентом. Не используй селекторы по тегам, в том числе в псевдоклассах, и сложные цепочки через родителей и соседей: смена тега или вложенности не должна ломать стили. Исключения для селекторов тегов — выделенные файлы глобальных стилей и их сброса, а также выделенный контейнер форматированного HTML-содержимого. Объявление `styled.button` допустимо.

```tsx
// Было
const Card = styled.div`h2 { margin: 0; }`;
<Card><h2>{title}</h2></Card>

// Стало
const Card = styled.div``;
const Title = styled.h2`margin: 0;`;
<Card><Title>{title}</Title></Card>
```

```css
/* Было */
.toolbar > button { padding: 8px; }
.card .body > .content .description { margin-top: 8px; }

/* Стало: классы назначены кнопке и описанию, в CSS Modules — через styles. */
.saveButton { padding: 8px; }
.description { margin-top: 8px; }
```

```css
/* Допустимо: reset.css и HTML статьи из редактора. */
html, body { margin: 0; }
button, input { font: inherit; }
.articleBody h2 { margin-top: 24px; }
.articleBody p { margin-bottom: 16px; }
```

Проверь происхождение HTML: имя `.content` или внешняя разметка календаря еще не говорят о том, что перед нами форматированное содержимое (попадающее под исключение). Вложенные библиотечные компоненты подчиняются [FF-DESIGN-002](#ff-design-002).

Автоматически заменяй селектор, только если известны все целевые элементы и сохранены каскад и состояния с учётом специфичности. Если имеем дело с неизвестной разметкой или внутренностями библиотеки спроси подтверждение, сразу код не меняй.

<a id="ff-react-001"></a>
## FF-REACT-001 — Компоненты вместо рендер-функций

**Область:** код приложения на React. Рендер-функция вызывается как обычная функция и собирает JSX для родителя; имя с `render` само по себе ничего не доказывает.

Выделяй такую разметку в компонент с явными пропсами. Объявляй его на уровне модуля в отдельном файле по [FF-REACT-002](#ff-react-002). Передавай данные и обработчики через пропсы; сохраняй `key`, порядок, условия и жизненный цикл.

```tsx
// Было: Profile.tsx
function Profile({ user, onEdit }) {
  const renderName = () => <button onClick={onEdit}>{user.name}</button>;
  return <section>{renderName()}</section>;
}

// Стало: ProfileName.tsx
export function ProfileName({ name, onEdit }) {
  return <button onClick={onEdit}>{name}</button>;
}
// Profile.tsx
import { ProfileName } from './ProfileName';
export function Profile({ user, onEdit }) {
  return <section><ProfileName name={user.name} onEdit={onEdit} /></section>;
}
```

```tsx
// Было
const renderItem = item => <li key={item.id}>{item.name}</li>;
<ul>{items.map(item => renderItem(item))}</ul>

// Стало: Item.tsx
export function Item({ item }) { return <li>{item.name}</li>; }
// List.tsx: key у непосредственного элемента массива.
import { Item } from './Item';
<ul>{items.map(item => <Item key={item.id} item={item} />)}</ul>
```

Допустимы рендер-функции, предусмотренные API компонента, и коллбеки событий/`map(callback)` и т.д.:

```tsx
<DataProvider>{data => <span>{data.name}</span>}</DataProvider>
<VirtualList renderItem={item => <Row item={item} />} />
<button onClick={() => save(id)}>Сохранить</button>
<ul>{items.map(item => <li key={item.id}>{item.name}</li>)}</ul>
const labels = items.map(item => item.name);
```

Проверяй контракт получателя коллбека. JSX внутри `.map()` допустим; отдельная рендер-функция, вызываемая из него, подпадает под правило.

Выделение компонента меняет дерево React. Проследи замыкания, хуки, ссылки `ref`, контекст, эффекты, мемоизацию и состояние. Объявление компонента внутри родителя создаёт новый тип при каждом рендере и может сбрасывать состояние. Если функция вызывает хуки или важны порядок вызовов, ссылки и сохранение экземпляров, нужен отдельный разбор. Пока сохранение поведения не подтверждено, оставь предложение. После исправления проверь обновление пропсов, аргументы обработчиков, перестановку списка, состояние и освобождение ресурсов.

<a id="ff-react-002"></a>
## FF-REACT-002 — Каждый компонент в отдельном файле

**Область:** функциональные и классовые компоненты приложения, включая локальные и обёрнутые в `memo` или `forwardRef`.

Каждый компонент размещай в отдельном файле независимо от размера и экспорта. Это даёт ему постоянное место и явные зависимости. Рядом могут оставаться типы, утилиты без компонентной разметки и объявления `styled`. Обёртка `memo`/`forwardRef` с реализацией и дополнительное имя экспорта не создают второй компонент.

```tsx
// Было: Panel.tsx
const Empty = () => <p>Пусто</p>;
export function Panel({ children }) { return children || <Empty />; }

// Стало: Empty.tsx
export const Empty = () => <p>Пусто</p>;
// Panel.tsx
import { Empty } from './Empty';
export function Panel({ children }) { return children || <Empty />; }
```

```tsx
// Было: Screen.tsx
const Hint = memo(function Hint() { return <small>Подсказка</small>; });
export function Screen() { return <Hint />; }

// Стало: Hint.tsx
export const Hint = memo(function Hint() { return <small>Подсказка</small>; });
// Screen.tsx
import { Hint } from './Hint';
export function Screen() { return <Hint />; }
```

Исключения:

```tsx
// Card.tsx: объявления styled и один компонент приложения.
const Root = styled.div``;
const Title = styled.h2``;
export function Card({ title }) { return <Root><Title>{title}</Title></Root>; }
// Card.test.tsx: тестовый компонент.
function TestProvider({ children }) { return <Provider>{children}</Provider>; }
// Card.stories.tsx: демонстрационные компоненты.
const Demo = () => <Card title="Пример" />;
const Playground = () => <><Demo /><Demo /></>;
```

Исключение определяется назначением: компонент, импортируемый приложением из теста или демонстрации, требует отдельного файла. Фабрика `styled` допустима, собственная функция с JSX считается компонентом. При переносе сохрани API, пропсы, `ref`, зависимости и порядок инициализации; проверь потребителей и тесты. Если перенос меняет границы модулей или создаёт цикл, оставь конкретное предложение.

<a id="ff-import-001"></a>
## FF-IMPORT-001 — Публичные импорты между модулями

**Область:** границы модулей, заданные документацией проекта, `package.json#exports`, алиасами путей и публичными точками входа. Каталог или файл `index` сам по себе не устанавливает границу.

Внешний потребитель импортирует через публичный `index` или объявленный путь пакета: перемещение реализации внутри модуля не должно затрагивать потребителей. Внутри модуля прямые импорты допустимы. Добавляй публичный экспорт, только если он соответствует назначению модуля и сохраняет порядок инициализации без циклов.

```ts
// Было: checkout/Checkout.tsx и checkout/model.ts
import { ProductCard } from '../catalog/components/ProductCard';
import type { Product } from '../catalog/model/types';

// Стало: catalog/index.ts уже экспортирует компонент и тип.
import { ProductCard } from '../catalog';
import type { Product } from '../catalog';
```

```ts
// Допустимо: прямой импорт внутри catalog, без цикла через собственный index.
// catalog/index.ts
export { ProductCard } from './components/ProductCard';
// catalog/components/ProductCard.tsx
import { selectProduct } from '../model/selectProduct';
// Допустимо: публичный путь ./button из package.json#exports.
import { Button } from '@team/ui/button';
```

Сохраняй документированный прямой внешний импорт для разрыва цикла или нужного порядка инициализации; укажи источник исключения. Если необходимость найдена только анализом зависимостей, сохрани код и предложи документировать решение.

До замены проверь реэкспорты, зависимости значений и типов, побочные эффекты, циклы и порядок инициализации в обе стороны. Сохраняй `import type`. Если публичного экспорта нет или `index` запускает побочные эффекты, предложи минимальный публичный API и нужную проверку. Автоматическая замена требует эквивалентности API и инициализации; перестройка модулей в правило не входит.

## FF-I18N-001 — FormattedMessage для локализованного JSX

**Область:** React-проекты, в которых уже используется `FormattedMessage`. Используй принятые в проекте импорты, объявления сообщений и способы передачи параметров. Если проект использует другую библиотеку локализации, это правило к нему не применяется.

Локализованное содержимое React выводи через `FormattedMessage`. Для потребителей строк сохраняй строковую локализацию.

```tsx
// Было
<h1>{intl.formatMessage(messages.title)}</h1>
<p>{intl.formatMessage(messages.greeting, { name })}</p>

// Стало
<h1><FormattedMessage {...messages.title} /></h1>
<p><FormattedMessage {...messages.greeting} values={{ name }} /></p>
```

```tsx
// Допустимо: потребителям нужны строки.
<input placeholder={intl.formatMessage(messages.search)} />
<button aria-label={intl.formatMessage(messages.close)} />
<img alt={intl.formatMessage(messages.cover)} />
useEffect(() => { document.title = intl.formatMessage(messages.title); }, [intl]);
const filtered = rows.filter(row => row.name.includes(intl.formatMessage(messages.query)));
```

Проверяй тип пропса: `title: string` требует строку, `children: ReactNode` может принимать компонент. Общий результат для строки и JSX нельзя целиком заменить элементом React. При другом стеке сохраняй его API, например `{t('title')}`.

Сохрани `id`, `defaultMessage`, `values`, локаль, провайдер, коллбеки форматирования, экранирование и обработку ошибок. Проверь версию: обёртки, `tagName` и фолбэк могут менять DOM и поведение. При неизвестном контексте, типе пропса или API оставь предложение. Удаляй строковый хук или импорт после проверки всех использований.

## FF-DESIGN — Работа с макетами

<a id="ff-design-001"></a>
### FF-DESIGN-001 — Прозрачность и пометки дизайнера

**Область:** перенос оформления из макета и сверка готового интерфейса с ним.

Полупрозрачность блока в Figma может обозначать часть макета без изменений (так дизайнеры обозначают, что в этом месте макет совпадает с тем, как уже сделано сейчас, либо как это сделано в других фреймах макета). Прежде чем переносить приглушение целого блока в интерфейс, проверь его назначение по пояснениям к макету, контексту задачи и подтверждённым решениям. Одно значение `opacity` не доказывает замысел дизайнера. При сомнении запроси уточнение у разработчика, сохрани спорный код и отметь непроверенную часть; независимую работу продолжай.

Подтверждённую пометку неизменённого блока не переноси в CSS: сохраняй согласованное оформление интерфейса. Запиши решение и учитывай его при финальной сверке с Figma. Если ответ уже есть, повторное согласование не нужно.

**Было:** «У списка показателей в макете `opacity: 0.4`; добавляю такую же прозрачность на страницу» — без проверки назначения.

**Стало:** «Дизайнер подтвердил: 40% обозначают неизменённый блок. Список сохраняет обычный вид без приглушения; это решение учитывается при сверке».

Настоящая прозрачность оформления, например декоративной сетки или недоступного элемента, сохраняется. Правило не разрешает автоматически заменять все дробные `opacity` на `1`.

<a id="ff-design-002"></a>
### FF-DESIGN-002 — Оформление компонентов UI-кита через публичный API

**Область:** потребители UI-кита, включая глобальные стили, CSS Modules, CSS-in-JS и форматированное содержимое.

Используй публичные пропсы, варианты и настройки темы из документации и типов установленной версии. Селекторы к внутренним классам, тегам и структуре DOM запрещены: обновление разметки библиотеки не должно ломать потребителя. Наличие класса в исходниках или DevTools не делает его публичным. Внешняя обёртка может управлять собственными отступами и расположением, не затрагивая внутренности компонента. Исключения [FF-CSS-002](#ff-css-002) эту границу не отменяют.

В примерах условный `@team/ui` документирует `Button.size`, `Button.variant` и `ThemeProvider.theme.controls.radius`; для реальной библиотеки проверь её API.

```css
/* Было: внутренний класс. */
.actions .uiButton__label { font-size: 14px; }
```

```tsx
// Стало: публичный размер.
<Button size="small">Сохранить</Button>
```

```css
/* Было: button принадлежит библиотеке, хотя находится внутри статьи. */
.richText button { border-radius: 8px; }
```

```tsx
// Стало: предусмотренная настройка темы.
<ThemeProvider theme={{ controls: { radius: 8 } }}><Button>Сохранить</Button></ThemeProvider>
```

```css
/* Было: внутренний структурный селектор. */
.actions > * > :first-child { color: white; }

/* Стало: обёртка оформляет себя, цвет задаёт Button.variant ниже. */
.actions { display: flex; gap: 8px; margin-top: 16px; }
```

```tsx
<div className="actions"><Button variant="primary">Сохранить</Button></div>
```

Используй `className`, API слотов и `styled(Button)`, только если библиотека документирует такой способ оформления. Стилизуй лишь тот элемент и те свойства, которые разрешает её публичный API. Не обращайся к внутренней разметке компонента через селекторы вроде `.customClass > span`. Для `styled(Button)` дополнительно проверь, что компонент передаёт `className` оформляемому DOM-элементу.

В контейнере HTML-статьи можно оформлять собственные заголовки, абзацы и другие теги по исключению FF-CSS-002. Если в статью вставлен компонент UI-кита, его оформляй через публичный API библиотеки.

До исправления установи владельца элемента, публичный API и влияние на все состояния. Автоматическая замена требует сохранения оформления и поведения: удаление стиля или класс на внутреннем узле этого не гарантируют. При нехватке данных сохрани код и запроси сведения; при конфликте с макетом примени [FF-DESIGN-004](#ff-design-004).

<a id="ff-design-003"></a>
### FF-DESIGN-003 — Переиспользование изображений

**Область:** добавленные и изменённые статичные изображения и их потребители.

Одинаковую иллюстрацию в разных частях макета используй из одного файла. Различия в размере, положении и простом кадрировании решай через CSS. Отдельные файлы оправданы другой композицией или требованиями к формату, разрешению и весу. Если переиспользование требует сложной сборки из слоёв или хрупкой вёрстки, используй готовый экспорт.

При объединении дублей обнови все ссылки и проверь результат на затронутых ширинах и DPR: композицию, кадрирование, прозрачность и качество. Экспорт и оптимизация должны сохранять вид иллюстрации; фон окружающей карточки оформляй контейнером. Заметные отличия от макета согласуй с разработчиком; непроверенное объединение оставь предложением.

**Было:** три копии одной иллюстрации для трёх карточек из разных фреймов.

**Стало:** один файл для трёх карточек; отдельный мобильный экспорт — если у него другая композиция.

<a id="ff-design-004"></a>
### FF-DESIGN-004 — Решение по небольшому отличию от макета

**Область:** небольшое отличие штатного компонента UI-кита от макета, устранимое только обходом публичного API.

Предложи разработчику принять конкретное отклонение. Укажи компонент, версию и API, маршрут, состояние, отличие с доступными измерениями и штатный вариант. Зависимая часть ждёт явного решения; спорный код сохраняй, независимые исправления продолжай. Малое отличие само по себе не означает согласия и не позволяет завершить эту часть задачи.

**Было:** «В макете радиус 6px, у Button — 8px. Отличие принято; задача завершена».

**Стало:** «На /checkout в обычном состоянии Button из @team/ui v2 имеет радиус 8px, в макете — 6px. Публичной настройки радиуса нет. Предлагаю оставить 8px; эта часть ждёт решения разработчика».

**Было:** «Для совпадения с макетом добавлен `.actions button > span { padding: 2px; }`».

**Стало:** «При загрузке внутренний отступ Button отличается на 2px. Публичные `size`/`variant` не помогают. Предлагаю штатный отступ; точное совпадение потребует отдельного изменения публичного API библиотеки».

Если не можешь открыть макет или проверить интерфейс, укажи, чего не хватает для сравнения. Если отклонение уже согласовано, приведи ссылку на решение и проверь, что оно относится к текущему компоненту и состоянию. Согласие оставить штатный вид компонента не даёт разрешения менять его внутреннюю разметку или стили. Если решение неясно, уточни его у разработчика, прежде чем менять дизайн или библиотеку.

## FF-VM-001 — Стабильные мапперы для .map()

**Область:** производные значения VM, особенно при повторных рендерах React.

Передавай в `.map()` один и тот же маппер, пока его зависимости не изменились: кеш производного состояния использует ссылку на функцию. Чистый маппер без захваченных переменных вынеси из рендера; маппер с зависимостями стабилизируй, указав их полностью. Инлайн-маппер при однократном создании поля VM допустим.

```tsx
// Было: новая функция на каждом рендере.
function Total({ vm }) {
  return <span>{vm.state.count.map(n => n * 2).signal}</span>;
}
// Стало
const double = (n: number) => n * 2;
function Total({ vm }) {
  return <span>{vm.state.count.map(double).signal}</span>;
}
```

```tsx
// Было: замыкание сохраняет старый factor.
const multiply = useCallback((n: number) => n * factor, []);
// Стало
const multiply = useCallback((n: number) => n * factor, [factor]);
const total = vm.state.count.map(multiply);
```

`readonly doubled = this.state.count.map(n => n * 2)` при создании VM допустимо. `Array.map` и обычные коллбеки вне области правила. `.bind()` внутри рендера создаёт новую ссылку. Чтение внешних изменяемых данных через `ref` или `get()` не подписывает состояние на их изменения; перенос и мемоизация должны сохранять обновления.

Если зависимости или владелец неясны, оставь предложение. Проверь рендер с прежними зависимостями, их смену и обновление источника. Кешируется базовое производное значение; обёртка React через `Proxy` может иметь новую ссылку.

## FF-VM-002 — .signal для вывода, .use() для значений

**Область:** состояние VM и `MappedState` с расширением для React.

Для непосредственного вывода в JSX используй `.signal`; для условий, вычислений рендера и атрибутов — значение из `.use()`. `.signal` — элемент React со своей подпиской, `.use()` — хук, подписывающий компонент. Вызывай его безусловно на верхнем уровне компонента или собственного хука, до ранних возвратов. `get()` не подписывает React на обновления.

```tsx
// Было: подписка всего компонента ради текста.
const count = vm.state.count.use();
return <span>{count}</span>;
// Стало
return <span>{vm.state.count.signal}</span>;
```

```tsx
// Было: элемент React в условии и атрибуте.
return vm.state.visible.signal ? <input disabled={vm.state.busy.signal} /> : null;
// Стало
const visible = vm.state.visible.use();
const busy = vm.state.busy.use();
return visible ? <input disabled={busy} /> : null;
```

Если значение из `.use()` уже нужно для условия, атрибута или вычисления, его можно вывести и в JSX без дополнительной подписки. Логическое значение само по себе не выводит текст; преобразуй его стабильным маппером. Для объектов также задай представление явно.

Вне рендера `get()` подходит для чтения текущего значения, например в обработчике; `.use()` в обработчике нарушает правила хуков. `.signal` — свойство: `.signal()` и `<state.signal />` неверны. При исправлении сохрани типы пропсов и проверь обновления текста, условий и атрибутов, а также порядок хуков.

## FF-VM-003 — Производное состояние только для чтения

**Область:** `MappedState` после `.map()` состояния с расширением для React, включая цепочки и вложенные поля.

Читай производное состояние через `get`/`use`/`signal`/`subscribe`/`map`; записывай в исходное изменяемое состояние через его публичную команду. У результата `.map()` нет публичных `set` и `destroy`; приведение типа не разрешает запись. В версии 2.0.2 запись отклоняется и при исполнении.

```ts
// Было
const doubled = vm.state.count.map(double);
doubled.set(10);
// Стало: если команда действительно должна задавать исходный count.
vm.state.count.set(5); // doubled теперь 10
```

```ts
// Было
const profile = vm.state.map(selectProfile);
profile.name.set(nextName);
// Стало: при подтверждённом соответствии profile исходному user.
vm.state.user.name.set(nextName);
```

Ошибочный `.set()` нужно заменить записью в исходное состояние, а не просто удалить: действие пользователя должно по-прежнему менять данные. Если непонятно, что записать в источник, уточни ожидаемое поведение у разработчика. Фильтрация, округление и суммирование могут терять данные, поэтому обратное преобразование не всегда однозначно.

После исправления проверь, что действие меняет исходное состояние, производное значение пересчитывается, а подписчики получают обновление. Проверка типов должна проходить без обхода через `any`/`as`. Освобождение VM описано в [FF-VM-004](#ff-vm-004).

## FF-VM-004 — Владелец и освобождение VM

**Область:** жизненный цикл VM, её владельца в React и общих долгоживущих экземпляров.

Владелец завершённого сценария освобождает VM через `vm.destroy()`: метод очищает состояние и отложенные ресурсы, вызывает `onDestroy`. Ручная очистка внутренних хранилищ Effector обходит этот контракт.

Для отложенного освобождения владеющий компонент безусловно вызывает `vm.useAutoDestroy()` на верхнем уровне, а логика сценария разрешает очистку через `vm.enableAutoDestroy()` в согласованный момент завершения. Разрешение не вызывает немедленный `destroy`; один `useAutoDestroy` без разрешения также не уничтожает VM.

```ts
// Было
clearNode(internalStore);
// Стало: в точке завершения сценария у владельца.
vm.destroy();
```

```tsx
// Было: хук в обработчике, ошибочное ожидание немедленной очистки.
const onFinish = () => {
  vm.useAutoDestroy();
  vm.enableAutoDestroy();
};
// Стало: после завершения владелец уходит, VM не используется повторно.
function FlowRoot({ vm }) {
  vm.useAutoDestroy();
  return <button onClick={() => vm.enableAutoDestroy()}>Завершить</button>;
}
```

Вне React владелец может вызвать `destroy` без `useAutoDestroy`. Дочерний экран не владеет общей VM многошагового сценария. Проверь `disableAutoDestroy` и сохранение VM между шагами. Не добавляй разрешение очистки автоматически при монтировании или рендере и не переноси уничтожение в очистку дочернего компонента без доказанного владения. Сохрани пользовательские коллбеки очистки, `onDestroy` и отмену внешних подписок; `destroy` не обещает отменить произвольный ввод-вывод.

В версии 2.0.2 `useAutoDestroy` использует эффект с зависимостями `[this, this.autoDestroyEnabled]`, а очистка читает текущее значение флага. Поэтому после `enableAutoDestroy` следующий рендер может освободить VM при смене зависимости, ещё до размонтирования. Для продолжающегося рендера нужна отдельная проверка или явное управление жизненным циклом; исправлять библиотеку в потребителе по догадке нельзя.

Проверь повторный рендер, размонтирование с разрешением и без него, однократный `onDestroy` при повторном `destroy` и недоступность освобождённого состояния. Для `StrictMode`, повторного монтирования и смены VM проверь контракт проекта: уничтоженный экземпляр нельзя автоматически использовать снова.
