# Оценка foxford-frontend-review 1.0.0 — ticket 01

Дата: 2026-10-16. Проверена устанавливаемая поставка CSS, без изменений существующих implement/code-review workflow. Это ограниченная поведенческая оценка инструкций агентом, не детерминированный CSS-линтер. Mixed/exception выполнены основным агентом; readonly/backend/insufficient — независимым Spec reviewer. В каждом случае прочитаны установленные SKILL.md и CODESTYLE.md, применена процедура к реальному Git-репозиторию.

## Установка

`npx --yes skills --version` → 1.7.2. Из пустого временного каталога выполнена команда `npx --yes skills add <adc-checkout>/delivery/skills/foxford-frontend-review --agent claude-code codex --copy --yes`, exit 0. После исправления инструкций установка повторена. Проверены .agents/skills и .claude/skills: все четыре файла побайтно равны исходникам, относительные ссылки разрешаются. `npx --yes skills list --json` вернул foxford-frontend-review с агентами claude-code и codex. Глобальные skills пользователя не изменялись. GitHub-установка неопубликованной ветки не проверена.

## Сценарии и результаты

| Сценарий | Результат | Доказательство |
|---|---|---|
| mixed: релевантный коммит + staged/unstaged + новые файлы | Три обычных дробных px исправлены; селектор заголовка заменён классом и изменена связанная разметка; серверный .ts, legacy и чужие правки сохранены | [Отчёт](mixed-report.md) |
| exception: документ проекта | Дроби в card.css сохранены по AGENTS.md; правило применяется к другому файлу, селектор исправлен | [Отчёт](exception-report.md) |
| readonly | Те же три px и селектор обнаружены, рабочие файлы и индекс не изменены | [Отчёт](readonly-report.md) |
| backend-only | «Неприменимо», серверный .ts с CSS-строками сохранён | [Отчёт](backend-report.md) |
| insufficient | «Неполная проверка», база и принадлежность неизвестного .ts не придуманы | [Отчёт](insufficient-report.md) |

Сохранены [исходные и конечные файлы, base/HEAD и diff](fixtures.json), а также [браузерные измерения](browser.json). Fixture содержит Node built-in smoke test контента и семантики, без внешних зависимостей. `node --test`: по одному успешному тесту для mixed, exception и readonly. Chrome DevTools MCP headless подтвердил сохранение H2, текста и цвета заголовка; mixed получил padding 16px / margin 8px, exception сохранил 15.999px / 7.999px. Повторная проверка обоих правил выполнена. Индекс и защищённые файлы сравнивались побайтно; readonly/backend/insufficient сохраняют все рабочие исходники.

В первом read-only прогоне обычные git status/diff обновили stat cache индекса при неизменных blob/mode/path. Исправлена процедура: GIT_OPTIONAL_LOCKS=0. Для чистого повторения в изолированных fixtures восстановлен исходный снимок индекса, затем все сравнения прошли. В правилах замены селектора уточнено сохранение фактического каскада после оценки изменения специфичности; на простом fixture результат подтверждён браузером.

## Проверки ADC и ограничения

Проверка метаданных, уникальности двух ID/якорей, ссылок, отсутствия локальных абсолютных путей в поставке и `git diff --cached --check` выполнена. Standards review: жёстких нарушений нет; замечание о ссылке на игнорируемый plans устранено переносом публичных доказательств сюда. Spec review: после исправления чтения Git пробелов в CSS scope не найдено.

Обязательные Go-гейты недоступны в этой хостовой среде: gofmt и go отсутствуют. Попытки `gofmt -l bin/adc`, `go vet ./...`, `go test -race ./...`, `go build -o .build/adc ./bin/adc` завершились command not found; профильный Go-тест метаданных также не запущен. Docker CLI есть, но daemon socket отсутствует; запасной контейнерный тулчейн недоступен. Установка Go или запуск Docker не выполнялись. Go-файлы и runtime не менялись; полноценные гейты остаются непроверенными.

Оценка не покрывает весь сложный CSS-in-JS, разные React runtime, неизвестную внешнюю разметку или все варианты каскада. Все заявленные исключения представлены в документе, но runtime-оценка использует ограниченный CSS/HTML fixture. Повторение сценариев и Go-гейты в подготовленной среде остаются обязательной частью дальнейшей проверки. Ticket не следует закрывать до прохождения обязательных проверок проекта.
