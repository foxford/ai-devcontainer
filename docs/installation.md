# Установка ADC

Если у вас уже работают devcontainer на старом ADC, начните с [порядка перехода с v0](migration.md). Установщик использует стандартные каталоги, сохраняет проверенную копию прежней платформы и заменяет adc в PATH. Данные агентов и томов копируются отдельной командой миграции.

Команды установки для macOS/Linux и Windows находятся в [README](../README.md#начать-работу). Скрипт сам клонирует платформу в пользовательский каталог или обновляет существующую установку.

## Поддерживаемые системы

ADC и Orca устанавливаются на Linux и macOS (amd64/arm64) и Windows (amd64). CLI также собирается для Windows arm64, но закреплённый релиз Orca содержит только пакет Windows x64.

Полная проверка установки и среды выполнена на Linux amd64. В CI настроены нативные проверки Go для Linux, macOS и Windows. Установка Docker Desktop и подключение хостовой Orca на macOS/Windows требуют проверки на этих ОС.

## Что делает установщик

Скрипт проверяет Git и средства загрузки, устанавливает недостающие компоненты, скачивает закреплённую версию Go с проверкой SHA-256 и собирает ADC. Go хранится в ADC_HOME/toolchains; устанавливать его в систему заранее не нужно. На Windows не требуется Bash, на хосте не нужны jq и rsync.

Далее `adc install` устанавливает бинарник, подключает PATH и автодополнение, проверяет Docker, устанавливает хостовую Orca и создаёт конфигурацию рабочей среды. Недостающий Docker устанавливается через apt/dnf/pacman на Linux, Homebrew Docker Desktop на macOS или winget Docker Desktop на Windows.

Установка системных компонентов может потребовать пароль администратора, UAC, повторный вход или перезагрузку. Установщик сообщает, что нужно сделать перед запуском среды, и продолжает установку остальных компонентов.

## Orca

Версия, ссылки на пакеты и SHA-256 закреплены в [runtime/orca-lock.json](../runtime/orca-lock.json). На Linux устанавливаются распакованный AppImage и пункт меню, на macOS приложение помещается в `~/Applications`, на Windows запускается официальный установщик.

На Linux установщик проверяет библиотеки Electron через `ldd` и устанавливает недостающие пакеты. Приложению Orca нужна графическая сессия. Сервер Orca работает внутри контейнера; его зависимости входят в образ.

Флаг `adc install --no-orca` пропускает установку хостового клиента Orca.

## PATH и автодополнение

ADC добавляет свой бинарник в пользовательский PATH и подключает автодополнение для Bash, Zsh, Fish и PowerShell. Установщик меняет только свои блоки в профилях оболочек; повторный запуск не создаёт дубликатов. После установки откройте новый терминал.

`adc workspace shell <project>` открывает Zsh внутри общей среды в каталоге проекта. При старте workspace ADC восстанавливает отсутствующие стандартные настройки оболочки после импорта профилей, сохраняя пользовательские настройки и авторизации. Повторная миграция для этого не требуется.

Команда автодополнения сохраняет скрипт в файл и показывает команды подключения для текущей сессии и профиля оболочки. Например, для Zsh:

```sh
adc completion zsh
```

На хосте Bash/Zsh сохраняются в ADC_HOME/completions, PowerShell — в ADC_HOME/completions/adc.ps1. Внутри runtime эти скрипты сохраняются отдельно в ~/.local/share/adc/completions. Zsh учитывает ZDOTDIR и включает compinit, если он ещё не запущен. Для Bash, Fish и PowerShell замените zsh в команде названием оболочки: bash, fish или powershell. Fish получает автозагружаемый файл в XDG_CONFIG_HOME/fish/completions или ~/.config/fish/completions. Команда completion сама не меняет профили: выполните показанную команду, если хотите подключить файл постоянно.

Полный текст скрипта выводится только с `--stdout`. Для перенаправления в собственный файл или `source <(...)` используйте этот флаг:

```sh
adc completion zsh --stdout > /path/to/adc.zsh
```

Флаг `--no-descriptions` убирает описания команд из автодополнения. Обычная установка по-прежнему сама сохраняет файлы и обновляет свои блоки в профилях.

Внутри среды установка и восстановление инструментов выполняются командой `adc tools install`. Graphify устанавливается для проектов с выбранной capability; OmniRoute поставляется вместе со штатными инструментами. Один инструмент можно восстановить отдельно: `adc tools install graphify` или `adc tools install omniroute`.

Claude устанавливается через [официальный npm-пакет](https://code.claude.com/docs/en/setup#install-with-npm), который поставляет нативный бинарник для платформы. Установщик сохраняет рабочие CLI и проверяет восстановленные командой --version. Настройки и сессии агентов остаются в общем home-томе.

## Обновление и диагностика

Команда `adc update` обновляет клон, пересобирает бинарник и образ, обновляет Orca и completion. Перед Git pull она проверяет локальные изменения платформы и незавершённое переключение контейнера. Сохраните изменения перед обновлением; если переключение ещё не завершено, выполните `adc workspace start`. При ошибке компилятора прежний бинарник остаётся на месте. Образ, параметры запуска и профили Docker подготавливаются до остановки работающей среды. Остановленный или ещё не созданный workspace остаётся остановленным; запуск: `adc workspace start`. Перезапуск завершает активные сеансы агентов; перед обновлением дождитесь завершения их задач. Повторный запуск команды установки также обновляет ADC и его настройки.

При замене контейнера ADC сохраняет прежний под именем `adc-<workspace>-previous-<token>` и удаляет его после подтверждения готовности нового. Если Docker не смог создать новый контейнер, ADC возвращает прежнему имя и запускает его, если он работал до переключения. Уже завершённые сеансы агентов при этом не возобновляются. Если подготовка нового runtime завершилась ошибкой, посмотрите `adc workspace logs`, исправьте причину и повторите `adc workspace start`: команда перезапустит неудачный runtime и дождётся готовности. При ошибке очистки старого контейнера повторный start завершает очистку.

Ctrl+C прекращает ожидание, а новый контейнер продолжает подготовку. Прежний контейнер и журнал ADC_HOME/workspace-replacement.json остаются до следующего `adc workspace start`, который подтвердит готовность и завершит переключение. После прерывания между остановкой и созданием контейнера эта же команда восстановит прежнее имя и повторит запуск. Не удаляйте журнал и резервный контейнер вручную; `adc workspace status` показывает незавершённое переключение. Конкурирующие команды обновления, запуска и остановки используют хостовые блокировки; runtime может синхронизировать конфигурации, пока хост ждёт готовности.

Восстановление контейнера сохраняет общие тома, авторизации и рабочие каталоги. Оно не возвращает прежнее содержимое томов, доставленных проектных файлов, клона платформы или установленного CLI. После Git pull клон может уже содержать новую версию, даже если сборка или запуск не удались. Новые сценарии восстановления проверены Go-тестами; подтверждение реальным Docker smoke для этого изменения ещё требуется.

На Windows прежний исполняемый файл может оставаться в ADC_HOME/bin/.adc-previous-*.exe, пока завершает работу процесс updater. После завершения процесса его можно удалить.

Если среда не запускается, начните с `adc doctor`, `adc workspace status` и `adc workspace logs`.

`adc workspace start` запускает контейнер в фоне, показывает этапы подготовки и возвращает консоль после готовности или ошибки. При долгом этапе каждые 15 секунд появляется сообщение с прошедшим временем. Ctrl+C прекращает ожидание; подготовка внутри контейнера продолжается. `adc workspace status` показывает готовность и текущий этап, а `adc workspace stop` останавливает сам контейнер с сохранением данных.

Временные ошибки DNS, соединения и HTTP повторяются с растущей паузой; установка имеет до пяти попыток, номер повтора виден в выводе. Ошибки доступа и отсутствующие пакеты завершаются сразу. Если повторы не помогли, проверьте сеть и снова запустите `adc workspace start`; импортировать профили повторно не нужно.

## Разработка установщика

Точка входа CLI находится в `bin/adc/`, хостовая логика в `bin/adc/host/`, доставка внутри контейнера в `bin/adc/runtime/`, общие операции в `bin/adc/internal/`. POSIX- и PowerShell-скрипты подготавливают машину к запуску бинарника.

Чтобы собрать CLI из локального клона:

```sh
go build -o .build/adc ./bin/adc
.build/adc --help
```

`.build/adc` — локальный бинарник для разработки. Установленная команда `adc` запускается напрямую. Проверки описаны в [AGENTS.md](../AGENTS.md#обязательные-гейты).

Если runtime перезапустился при установке, `adc workspace status` покажет текущий этап нового запуска, а `adc workspace logs` — причину предыдущего выхода. Рабочие инструменты в общем томе сохраняются. Установщик OpenCode повторяется также при тихой ошибке DNS: curl возвращает код 6 без текста ошибки.

Установочные Git-запросы прерываются, если HTTP-передача 30 секунд идёт со скоростью менее 1 байта/с. Такая ошибка допускает повтор установки; общий срок клонирования этим правилом не ограничивается. В git config пользователя ничего не записывается.

После миграции ADC исправляет документные ссылки на известные старые пути платформы. Скиллы в .claude/skills без маркера ADC сохраняются как пользовательские, даже если их имена совпадают с платформенными; для управляемого форка перенесите их в .agents/skills. Ошибка доставки одного проекта не завершает Orca: start возвращает конкретную ошибку, status показывает running с ошибкой подготовки. Исправьте указанные файлы, повторите adc sync и выполните adc workspace stop, затем adc workspace start для проверки всей среды.
