# Skill: Senior Frontend — вход во все задачи про интерфейс

Этот скилл — **диспетчер**, а не единственный исполнитель. Рядом лежат сильные
дизайн-скиллы, и каждый из них умеет больше, чем этот. Но каждый из них при этом
готов переписать проекту типографику, палитру и сетку по собственному вкусу, если
его позвать без рамки. Рамку ставит этот файл.

## Главное правило

> **Нет явного требования по дизайну — значит требование одно: попасть в то, что
> уже есть.** Новый экран собирается из существующих компонентов и токенов, в той
> же манере, что соседний код. Шрифт, палитра, радиусы, сетка, плотность,
> характер анимации — не решения агента, а факт, который надо вычитать из проекта.

Это правило перекрывает любые «BANNED / ALWAYS / NEVER» из соседних дизайн-скиллов.
Их запреты («Inter забанен», «три равные карточки забанены», «центрированный герой
забанен», «первым делом меняй шрифт») написаны для **нового визуального мира**.
В живом проекте это не основание что-то менять — это в лучшем случае аргумент
в разговоре с человеком.

Сомневаешься, есть ли мандат на дизайн, — **мандата нет**.

## Мандат на дизайн: три уровня

Определи уровень **до** того, как открыл дизайн-скилл. От него зависит и маршрут,
и то, что вообще разрешено трогать.

| | Когда это | Что можно менять | Кого зовём |
|---|---|---|---|
| **A. Встроиться** (по умолчанию) | «сделай форму», «добавь колонку», «почини вёрстку», «выведи список» — про функциональность | ничего сверх задачи; визуал наследуется | только этот скилл + `playwright-pro` |
| **B. Улучшить в рамках системы** | «выглядит криво», «поправь отступы», «неудобно», «добавь состояние загрузки» | внутри существующих токенов и компонентов; новые токены — только если без них никак, и это проговаривается | `impeccable` (`polish`/`layout`/`clarify`/`audit`), `redesign-existing-projects` как чек-лист |
| **C. Новый визуальный мир** | человек прямо просит редизайн, новый лендинг, новый продукт, «сделай красиво по-своему», принёс референсы | всё в границах названной поверхности | `design-taste-frontend`, `impeccable` (`new-work`/`bolder`/`animate`), `brandkit`, `redesign-existing-projects` |

Уровень C **не выводится** из того, что интерфейс выглядит средне. Он объявляется
человеком. Если задача уровня A, а по дороге видно системную проблему — скажи о ней
одной фразой и продолжай задачу; предложение редизайна это отдельный разговор.

Границы уровня C тоже узкие: «переделай лендинг» — это лендинг, а не дизайн-система
всего репозитория. Правка общих токенов задевает все экраны разом и делается только
явно.

## Откуда берётся стайлгайд

Ищи в этом порядке и остановись на первом, что нашлось. Найденное — источник правды.

1. **`DESIGN.md`** аппа или корня (конвенция `impeccable`), рядом `PRODUCT.md`.
2. **`SPEC.md`** затронутого аппа/пакета — раздел про UI и принятые решения.
3. **Токены**: `tailwind.config.*`, `theme.css`, `globals.css`, `:root { --… }`,
   `tokens.ts`, тема UI-библиотеки. Читаем значения, а не догадываемся.
4. **Ближайшие соседи по коду** — два-три компонента из той же зоны. Как у них
   устроены пропсы, варианты, классы, состояния — так и у нового.
5. **Конфиги**: `eslint.config.*`, `prettier.config.*`, `package.json` —
   что за стек, какие библиотеки уже есть, какая мажорная версия Tailwind.

**Пусто на первых четырёх пунктах — это не greenfield.** Сосед по коду есть почти
всегда, и он и есть стайлгайд. Настоящий greenfield — это когда каталога ещё нет.

Расхождение `DESIGN.md` и кода — **сообщи, не чини молча**: непонятно, что из
двух устарело, а тихий выбор в пользу одного ломает второе.

## Маршрутизация

| Задача | Куда идти | Уровень |
|---|---|---|
| Новый экран/компонент в существующем аппе | этот скилл + соседи по коду | A |
| Вёрстка поехала, отступы, выравнивание, ритм | `impeccable` → `layout` | A–B |
| Финальная вычитка перед сдачей | `impeccable` → `polish` | B |
| Тексты интерфейса, ошибки, лейблы | `impeccable` → `clarify`, затем `humanizer` по тексту | B |
| Доступность, адаптив, технический аудит | `impeccable` → `audit` / `adapt` | B |
| Пустые состояния, загрузка, ошибки, i18n | `impeccable` → `harden` / `onboard` | B |
| Медленный интерфейс, дёрганая анимация | `impeccable` → `optimize`, профилирование — MCP `chrome-devtools` | A–B |
| Чек-лист «что здесь выглядит как сгенерённое» | `redesign-existing-projects` (**как список вопросов, не как список правок**) | B–C |
| Новый лендинг, портфолио, редизайн поверхности | `design-taste-frontend` | C |
| Новый визуальный мир для продукта, замена DESIGN.md | `impeccable` → `new-work`, затем `document` | C |
| Логотип, брендборд, айдентика, презентация бренда | `brandkit` | C |
| `DESIGN.md` под генерацию экранов в Google Stitch | `stitch-design-taste` | C |
| Посмотреть на живой интерфейс, снять консоль, скриншот | `playwright-pro` + MCP `browser_*` | любой |
| Закрепить поведение тестом | `playwright-pro` (e2e), `senior-qa` / `vitest-testing` (компонентные) | любой |
| Новый пакет или апп в монорепе | `package-scaffold`, затем `nx-monorepo` | — |
| Ошибки типов, строгий TS | `typescript-strict` | — |
| Правки правил линтинга | `eslint-config-authoring` | — |
| Тяжёлые зависимости, CVE, лицензии | `dependency-auditor` | — |

Полный список скиллов с описаниями — `AGENTS.skills.md` в корне проекта.

**Один дизайн-скилл за раз.** Открыл `impeccable` — доведи ветку до конца, прежде
чем открывать `design-taste-frontend`. Смешивать их директивы нельзя: у них разные
дефолты по стеку, иконкам и шрифтам, и вместе они дают кашу.

### Что в соседних скиллах игнорировать

Все они пришли извне и написаны про «свой проект с нуля». Внутри монорепы foxford
не применяй из них:

- **Установку зависимостей.** «Поставь Motion», «поставь Phosphor», «поставь shadcn»,
  `npx shadcn@latest add …` — только с явного разрешения человека. Правило платформы
  сильнее рекомендации скилла.
- **Смену стека.** Миграции Tailwind v3 → v4, замену стилевой системы, переход на
  другой фреймворк или роутер по своей инициативе не делаем.
- **Безусловные баны шрифтов и иконок.** `Inter` забанен, `lucide-react` не
  рекомендован, serif «очень не рекомендован» — это дефолты для нового мира.
  Проект уже сделал свой выбор; менять его — уровень C и отдельный разговор.
- **`npm` / `yarn`.** В репозитории `pnpm` и `nx`. Команды из чужих скиллов
  переводи на них.
- **Хуки `impeccable`.** `$impeccable hooks on` ставит детектор, который сам
  запускается после правок UI. Включать — только если человек попросил.
- **Побочные записи файлов.** `init`, `document`, `extract` создают `PRODUCT.md`,
  `DESIGN.md`, `.impeccable/`. Это заметный след в репозитории — предупреди перед тем,
  как их звать.

### Скрипты этого скилла

`scripts/frontend_scaffolder.py` и `scripts/component_generator.py` генерируют
проект и компоненты под `npm` + свою структуру каталогов. **В монорепе foxford их
не используем**: новый пакет — `package-scaffold`, новый компонент — руками по
образцу соседа. `scripts/bundle_analyzer.py` и `scripts/frontend_decision_engine.py`
безвредны — читают и считают, ничего не пишут.

## Порядок работы

1. **Определи уровень мандата** (A/B/C). Не уверен — A.
2. **Прочитай спеку.** `SPEC.md` затронутого аппа обязателен; для уровня B/C — ещё
   и `DESIGN.md`.
3. **Вычитай стайлгайд** по списку выше. Выпиши для себя: шрифты, шкала, палитра,
   радиусы, спейсинг, как в проекте делают варианты компонентов.
4. **Позови нужный скилл** по таблице маршрутизации — если он вообще нужен.
5. **Сделай правку** в манере соседнего кода. Семантический HTML, доступность
   с клавиатуры, видимый фокус, состояния загрузки/пустое/ошибка — не «полировка
   потом», а часть задачи.
6. **Посмотри глазами.** См. ниже.
7. **Прогони quality gates** (`lint:eslint`, `lint:type-check`, `test`) и закрепи
   поведение тестом, если оно того стоит.
8. **Обнови `SPEC.md`**, если изменилось поведение или решение, а не только пиксели.

## Проверка в браузере

Правка вёрстки, роутинга или чего-то, что видно, — **не сдаётся без взгляда**.
Браузер есть: MCP-сервер `playwright`, инструменты `browser_*`.

- `browser_snapshot` — по умолчанию: дерево доступности текстом, дёшево и сразу
  показывает роли, имена и дыры в семантике. Скриншот — когда вопрос про внешний вид.
- Смотри **оба размера**: десктоп и мобильный (`browser_resize`). «На десктопе
  нормально» — это половина ответа.
- `browser_console_messages` после взаимодействия: ошибка в консоли — часть результата.
- Профилирование, троттлинг, Core Web Vitals — второй сервер, `chrome-devtools`.

Разведка браузером не заменяет тест. Нашёл поведение, которое надо зафиксировать, —
`playwright-pro`, тест в `e2e/`.

Проверяй **батчами, а не в цикле**: собрал целиком → один заход осмотра (десктоп
и мобильный вместе) → починил всё найденное разом → максимум один подтверждающий
заход → стоп.

## Ревью чужого фронтенда

Смотри в этом порядке — сверху вниз по цене ошибки:

1. **Соответствие проекту** — новый код в манере существующего или изобретает свою?
2. **Семантика и доступность** — `<button>` вместо `<div onClick>`, метки,
   контраст, фокус, навигация с клавиатуры.
3. **Состояния** — загрузка, пусто, ошибка, длинный текст, отсутствие данных.
4. **Адаптив** — узкий экран, длинные слова, зум 200%.
5. **Производительность** — что попало в клиентский бандл, что перерисовывается,
   не в `useState` ли непрерывные значения (скролл, курсор).
6. **Вкус** — в последнюю очередь и только если есть мандат.

## Бюджеты и критерии

Для нового аппа или разговора про производительность цифры называются явно, иначе
«быстро» ничего не значит:

| Профиль | Когда | LCP (mobile-4G p75) | JS на маршрут |
|---|---|---|---|
| `next-app-router` | SaaS, SEO + динамика, RSC | 2000 мс | 150 KB-gzip |
| `remix-or-sveltekit` | мобильный трафик, минимум JS | 1500 мс | 80 KB-gzip |
| `vite-spa` | за логином, десктоп | 2500 мс | 200 KB старт + 80 KB маршрут |
| `astro-or-static` | маркетинг, доки, блог | 1200 мс | 30 KB на страницу |

Плюс INP < 200 мс и CLS < 0.1 везде.
