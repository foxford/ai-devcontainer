# Проверка frontend-договорённостей

## 1. Зафиксировать область

Прочитай запрос задачи, инструкции затронутого проекта и его команды проверок. Зафиксируй режим: по умолчанию исправление; «без изменений», «только замечания» или read-only означают только отчёт, без записи в рабочие файлы, индекс и конфиги и без запуска изменяющих их проверок.

Определи базовый коммит и состав задачи из переданных base/PR/тикета и истории ветки. Проверь, что база существует. Сохрани SHA базы и HEAD, список релевантных коммитов и исходное состояние `git status --short`, staged, unstaged и новых файлов. Для чтения Git задай `GIT_OPTIONAL_LOCKS=0`, чтобы команды просмотра не обновляли индекс. Используй `git log`, `git diff <base>...HEAD`, `git diff --cached`, `git diff` и `git ls-files --others --exclude-standard`. Эти источники вместе задают область: проверяй итоговое содержимое рабочих файлов с привязкой к изменениям задачи, включая её новые файлы. Для удалений оцени последствия в оставшемся коде.

Отдели незавершённые пользовательские изменения вне задачи, включая соседние строки того же файла. Сохраняй их побайтно; индекс оставь как был. Соседний legacy-код читай для понимания, исправляй только внесённые задачей нарушения и минимально необходимые связанные места. При невозможности обоснованно выбрать базу или отделить изменения запроси недостающие сведения и продолжи независимую часть без записи в спорные места. Статус этой проверки — «неполная», даже если в доступной части нет замечаний. История всей сессии и произвольно выбранный HEAD~1 не определяют задачу.

Для каждого изменённого файла установи назначение по расположению, package manifest, импортам, вызовам и документации: frontend, backend, общий модуль или неизвестно. Расширение само по себе не доказывает применимость: серверный .ts может содержать строки с CSS, а frontend CSS может находиться в .tsx. В смешанном diff проверяй frontend-часть и доказанно относящиеся к ней участки общих модулей. Если frontend-изменений нет, верни «неприменимо» с основанием и заверши без правок. Неизвестная роль файла означает неполноту, а не успешный пропуск.

Критерий шага: известны режим, база, изменения задачи и применимость каждого файла либо явно перечислены пробелы контекста.

## 2. Прочитать правила и проверить

Для применимой части полностью прочитай соседний [CODESTYLE.md](CODESTYLE.md). Это единственный нормативный источник; нормативные требования, причины и исключения бери из него. Применяй только опубликованные там правила в их области. Для выбора применимых разделов проверь назначение кода, границы модулей, стек локализации, импорты и поддерживаемую версию API. Наличие frontend-файла не делает все правила применимыми; неопубликованные правила не изобретай.

Явная документированная договорённость проекта имеет приоритет: запиши источник и область переопределения в отчёт. Один похожий пример в старом коде исключением не считается. Для каждого применимого правила проверь все относящиеся к задаче участки, допустимые парные случаи и исключения. Поиск текстовых совпадений используй как подсказку, затем читай определения, потребителей и связанную разметку: совпадение имени функции, callback, строка и настоящий селектор требуют разного решения.

Критерий шага: каждое применимое правило проверено в установленной области; у замечания есть файл:строка, ID, ссылка и основание.

## 3. Исправить и подтвердить

В обычном режиме сразу исправь однозначные нарушения без подтверждения каждой правки. До записи проверь, что прочитанный участок не изменился; при конкурентных изменениях перечитай его. Для неоднозначной правки опиши конкретное предложение и недостающие сведения, сохрани исходный код. При замене селектора проследи все затронутые элементы и состояния, оцени изменение специфичности и сохрани фактический каскад, обработчики и публичные контракты. Для структурных исправлений выполни проверки сохранения поведения из соответствующего раздела CODESTYLE.md. Если это доказать нельзя, оставь предложение.

В режиме без изменений закончи отчётом о найденном; даже очевидное нарушение остаётся предложением. При независимых параллельных review все проверяющие читают одну зафиксированную версию без записи; один владелец применяет согласованные исправления после их завершения. Этот skill сам не запускает параллельных агентов.

После исправления выполни проверки проекта, необходимые для затронутого поведения: доступные lint, типы, профильные тесты, при изменении оформления — принятую в проекте браузерную проверку затронутых состояний. Команды находи в проекте, соблюдай его инструкции. Недоступную, упавшую или пропущенную проверку отрази фактически, без заявления об успехе. Повторно проверь затронутые правила на конечном diff и убедись, что пользовательские изменения вне задачи и индекс сохранены. При новых однозначных нарушениях повтори цикл; оставшиеся проблемы перечисли.

Критерий шага: исправления подтверждены повторной проверкой правил и необходимыми проектными проверками либо результат явно неполный.

## 4. Отчитаться

Укажи режим, base/HEAD, релевантные коммиты, рабочие изменения и новые файлы, проверенную frontend-область и пропущенную backend-часть с основаниями. Статус: «проверено», «неприменимо» или «неполная проверка»; оставшиеся нарушения перечисли независимо от статуса.

Для каждого замечания дай место, [ID и ссылку на правило](CODESTYLE.md), выполненное исправление либо отдельное предложение. Перечисли применённые исключения и приоритетные проектные документы. Покажи команды и фактические результаты проверок, результат повторной проверки правил и ограничения. При отсутствии замечаний назови проверенные правила и область. Не объявляй непроверенные случаи успешными.

## Установка и подключение

Инструкции установки и воспроизводимой оценки: [USAGE.md](USAGE.md). Для будущего подключения к implement точка вызова — после независимых code-review и до коммита, с той же базой и включением рабочего результата. Установка не изменяет существующие workflows и не гарантирует автоматический вызов. Commit, push и публикация выполняются только по отдельному поручению.
