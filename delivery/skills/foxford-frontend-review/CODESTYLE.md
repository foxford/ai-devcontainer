## FF-CSS-001 — Целые px для обычных размеров и отступов

**Область:** CSS, CSS Modules, CSS-in-JS и inline styles frontend-компонентов; числовые значения, для которых API подразумевает px, также входят в область. Числа в серверной логике или в тексте страницы не являются CSS-размерами.

**Требование:** обычные размеры и отступы задаются целыми px. Избыточную точность из макета убирают. Намеренные дробные px с понятной причиной сохраняют. Коэффициенты, проценты и углы это правило не округляет. Правило не требует заменять арифметические выражения готовыми значениями.

**Причина:** случайная точность из макетов усложняет чтение и создаёт непреднамеренное выравнивание на доли пикселя. При этом дробные значения нужны для отдельных визуальных эффектов и расчётов.

### Парные примеры

Как не надо — лишняя точность обычного отступа:

```css
.card { padding: 15.999px; }
```

Как надо — намеренный размер:

```css
.card { padding: 16px; }
```

Как не надо — перенесённая из макета ширина кнопки:

```tsx
const Button = styled.button`width: 119.999px;`;
```

Как надо:

```tsx
const Button = styled.button`width: 120px;`;
```

Как не надо — та же избыточная точность в inline style:

```tsx
<div style={{ marginTop: 7.999 }} />
```

Как надо:

```tsx
<div style={{ marginTop: 8 }} />
```

### Исключения и границы

```css
/* Тонкая линия для целевых экранов с DPR 2: намеренная половина CSS px. */
.separator { border-bottom: 0.5px solid currentColor; }
/* Дробный сдвиг компенсирует оптический центр конкретной иконки. */
.icon { transform: translateX(0.5px); }
.text { line-height: 1.5; opacity: 0.75; }
.column { width: 33.333%; transform: rotate(22.5deg); }
.layout { width: calc(100% - 16px); padding: calc(8px * 2); }
```

Динамические вычисления и намеренные дробные значения сохраняют вместе с их причиной из документации, кода или проверяемого контекста. Если назначение дроби или целое целевое значение неоднозначны, предложи уточнение вместо слепого округления всех чисел. Комментарий помогает передать причину, но не обязателен, если она уже подтверждена контекстом.

## FF-CSS-002 — Явное оформление собственных компонентов

**Область:** компонентные frontend-стили, включая вложенные селекторы CSS-in-JS и CSS Modules. Селектор типа, в том числе в цепочке или псевдоклассе, связывает оформление с HTML-тегом. Выбор тега через `styled.button` создаёт собственный компонент и сам по себе не нарушает правило.

**Требование:** собственные элементы оформляют явными классами или styled-компонентами вместо селекторов тегов. Исключения — global/reset и выделенные стили rich text внутри контейнера контента. Приоритетный документ проекта может уточнить область. Сам факт внешнего происхождения разметки исключением не является.

**Причина:** замена семантического тега или добавление вложенного элемента не должна случайно менять оформление соседних элементов. Явный контракт оформления показывает, какой элемент получает стиль.

### Парные примеры

Как не надо:

```tsx
const Card = styled.div`h2 { margin: 0; }`;
<Card><h2>{title}</h2></Card>
```

Как надо:

```tsx
const Card = styled.div``;
const Title = styled.h2`margin: 0;`;
<Card><Title>{title}</Title></Card>
```

Как не надо — CSS и связанная разметка:

```css
.toolbar > button { padding: 8px; }
```

```html
<div class="toolbar"><button>Сохранить</button></div>
```

Как надо — класс описывает назначение:

```css
.toolbar > .saveButton { padding: 8px; }
```

```html
<div class="toolbar"><button class="saveButton">Сохранить</button></div>
```

Как не надо — вложенный селектор CSS Modules:

```css
.card p { margin-top: 8px; }
```

Как надо — явный класс описания, назначенный соответствующему элементу через `styles.description`:

```css
.card .description { margin-top: 8px; }
```

### Исключения и границы

Допустимо глобальное начальное оформление и reset в предназначенных для этого файлах:

```css
/* reset.css — глобальный reset проекта */
html, body { margin: 0; }
button, input { font: inherit; }
```

Допустимы селекторы тегов для rich text в выделенном контейнере контента:

```css
/* .articleBody содержит HTML статьи из редактора контента. */
.articleBody h2 { margin-top: 24px; }
.articleBody p { margin-bottom: 16px; }
```

Название `.content` само по себе не доказывает rich text; проверь происхождение и назначение HTML. Компонент с внешней разметкой, например библиотечный date picker, не становится rich text. Это исключение не разрешает обходить публичный API UI-kit и переопределять его внутренние классы, теги или DOM-структуру.

Автоматическая замена допустима, когда известны все соответствующие элементы и можно подтвердить сохранение каскада и состояний с учётом изменения специфичности. Если разметка недоступна, селектор влияет на несколько неизвестных веток или относится к внутренностям библиотеки, верни предложение с описанием нужного публичного контракта вместо механического добавления класса.

## FF-REACT-001 — Компоненты вместо JSX render helpers

**Область:** React-код production. Render helper — вызываемая как обычная функция подпрограмма, которая собирает JSX для родительского компонента. Имя с `render` само по себе не доказывает нарушение.

**Требование:** такую разметку выделяют в React-компонент с явными props. Компонент объявляют на уровне модуля в отдельном файле по [FF-REACT-002](#ff-react-002). Данные и обработчики передают через props; сохраняют keys, порядок элементов, условия и жизненный цикл.

**Причина:** явная компонентная граница делает зависимости разметки видимыми и позволяет React управлять её жизненным циклом.

### Парные примеры

Как не надо — helper замыкает данные родителя:

```tsx
function Profile({ user, onEdit }) {
  const renderName = () => <button onClick={onEdit}>{user.name}</button>;
  return <section>{renderName()}</section>;
}
```

Как надо — два файла:

```tsx
// ProfileName.tsx
export function ProfileName({ name, onEdit }) {
  return <button onClick={onEdit}>{name}</button>;
}
// Profile.tsx
import { ProfileName } from './ProfileName';
export function Profile({ user, onEdit }) {
  return <section><ProfileName name={user.name} onEdit={onEdit} /></section>;
}
```

Как не надо — helper вызывается для элементов списка:

```tsx
const renderItem = item => <li key={item.id}>{item.name}</li>;
<ul>{items.map(item => renderItem(item))}</ul>
```

Как надо — key остаётся на непосредственном элементе массива:

```tsx
// Item.tsx
export function Item({ item }) { return <li>{item.name}</li>; }
// List.tsx (фрагмент)
import { Item } from './Item';
<ul>{items.map(item => <Item key={item.id} item={item} />)}</ul>
```

### Исключения и границы

Render props — штатный контракт принимающего компонента, а callbacks событий и коллекций допустимы:

```tsx
<DataProvider>{data => <span>{data.name}</span>}</DataProvider>
<VirtualList renderItem={item => <Row item={item} />} />
<button onClick={() => save(id)}>Сохранить</button>
<ul>{items.map(item => <li key={item.id}>{item.name}</li>)}</ul>
const labels = items.map(item => item.name);
```

Проверь контракт получателя callback, а не только возвращаемый JSX. Не превращай render prop в компонент механически. Обычный `.map()` с JSX сам по себе не helper; отдельная функция сборки разметки, вызываемая из него, попадает под правило.

Выделение компонента меняет дерево React. До исправления проследи замыкания, hooks, refs, context, эффекты, мемоизацию и состояние. Новое определение внутри родительского render создаёт новый тип при каждом вызове и может сбрасывать состояние. Hooks в обычном helper, зависимости от порядка вызовов, ref или требование сохранить identity требуют отдельного разбора; если сохранение поведения не подтверждается, оставь предложение. После однозначного выделения проверь обновление props, вызов обработчика с теми же аргументами, перестановку списка с keys и сохранение состояния/cleanup там, где они есть.

## FF-REACT-002 — Один production React-компонент на файл

**Область:** production React-компоненты: функциональные, классовые, обёрнутые в `memo` или `forwardRef`, включая небольшие локальные компоненты.

**Требование:** каждый компонент имеет отдельный файл. Размер и отсутствие экспорта не являются исключениями. Связанные типы, утилиты без компонентной разметки и styled declarations могут оставаться рядом. Обёртка `memo`/`forwardRef` и её реализация образуют один компонент; публичный alias не создаёт второй.

**Причина:** отдельный файл даёт компоненту постоянное место и позволяет читать его зависимости независимо от родителя.

### Парные примеры

Как не надо:

```tsx
// Panel.tsx
const Empty = () => <p>Пусто</p>;
export function Panel({ children }) { return children || <Empty />; }
```

Как надо:

```tsx
// Empty.tsx
export const Empty = () => <p>Пусто</p>;
// Panel.tsx
import { Empty } from './Empty';
export function Panel({ children }) { return children || <Empty />; }
```

Как не надо — memo не делает второй компонент исключением:

```tsx
// Screen.tsx
const Hint = memo(function Hint() { return <small>Подсказка</small>; });
export function Screen() { return <Hint />; }
```

Как надо:

```tsx
// Hint.tsx
export const Hint = memo(function Hint() { return <small>Подсказка</small>; });
// Screen.tsx
import { Hint } from './Hint';
export function Screen() { return <Hint />; }
```

### Исключения и границы

```tsx
// Card.tsx — styled declarations и один production-компонент
const Root = styled.div``;
const Title = styled.h2``;
export function Card({ title }) { return <Root><Title>{title}</Title></Root>; }
// Card.test.tsx — тестовая фикстура
function TestProvider({ children }) { return <Provider>{children}</Provider>; }
// Card.stories.tsx — демонстрационные компоненты
const Demo = () => <Card title="Пример" />;
const Playground = () => <><Demo /><Demo /></>;
```

Исключение определяется назначением компонента, а не одним суффиксом файла: production-компонент, импортируемый приложением из stories или теста, требует отдельного production-файла. Фабрика `styled` — declaration, собственная функция-обёртка с JSX — компонент. При переносе сохрани экспортируемый API, props, refs, зависимости и порядок инициализации; проверь потребителей и тесты. Если перенос требует изменения границ модулей или опасного цикла, предложи конкретный перенос без автоматической перестройки архитектуры.

## FF-IMPORT-001 — Публичный index-контракт между модулями

**Область:** импорты между установленными в проекте модулями frontend-кода. Границу определяют локальные документы, package exports, aliases и существующий публичный entry point, а не каждый каталог. Существование любого index-файла само по себе не доказывает границу модуля.

**Требование:** внешний потребитель использует публичный index-контракт модуля вместо доступа к его реализации. Необходимые прямые внутренние импорты сохраняют. Публичный экспорт добавляют только если это соответствует назначению модуля и не создаёт цикл или ошибку инициализации.

**Причина:** внешний код зависит от поддерживаемого API, поэтому перемещение реализации внутри модуля не затрагивает потребителей.

### Парные примеры

Как не надо — `catalog/index.ts` уже экспортирует ProductCard:

```ts
// checkout/Checkout.tsx
import { ProductCard } from '../catalog/components/ProductCard';
```

Как надо:

```ts
import { ProductCard } from '../catalog';
```

Как не надо — тип также является частью публичного контракта:

```ts
// checkout/model.ts
import type { Product } from '../catalog/model/types';
```

Как надо — `catalog/index.ts` содержит `export type { Product } from './model/types'`:

```ts
import type { Product } from '../catalog';
```

### Исключения и границы

Внутри модуля допустим прямой импорт, в том числе для предотвращения self-barrel цикла:

```ts
// catalog/index.ts
export { ProductCard } from './components/ProductCard';
// catalog/components/ProductCard.tsx
import { selectProduct } from '../model/selectProduct';
```

Явный subpath из `package.json` exports является публичным API; его сохраняют, даже если у пакета есть корневой index:

```ts
import { Button } from '@team/ui/button'; // package exports: ./button
```

Прямой внешний импорт, документированный проектом как необходимый для разрыва цикла/порядка инициализации, сохраняют и отмечают с источником. Если необходимость обнаружена анализом графа без документа, сохрани код и опиши причину как предложение, а не скрывай нарушение за ссылкой на legacy.

До замены проследи реэкспорты, runtime- и type-only зависимости, side effects, циклы и порядок инициализации в обе стороны. Type-only импорт не превращают в runtime. Если публичного экспорта нет или index подтягивает side effects, нельзя автоматически экспортировать все внутренности: предложи минимальный контракт и недостающую проверку. Автоматическая замена допустима только при подтверждённой эквивалентности API и инициализации; широкая перестройка модулей вне области.

## FF-I18N-001 — FormattedMessage для локализованного JSX

**Область:** React-проекты с i18n-стеком, который уже поддерживает `FormattedMessage` (например, установленный react-intl соответствующей версии). Способ импорта, descriptors, values и rich text определяют по фактическому API проекта. Правило не требует установки другого стека.

**Требование:** локализованный React-контент выводят через `FormattedMessage`. Для API, которому нужна строка, сохраняют строковый способ локализации.

**Причина:** компонентный API выражает назначение React-контента и поддерживает принятый в проекте вывод сообщений; строковые потребители сохраняют свой контракт.

### Парные примеры

Как не надо:

```tsx
<h1>{intl.formatMessage(messages.title)}</h1>
```

Как надо:

```tsx
<h1><FormattedMessage {...messages.title} /></h1>
```

Как не надо — JSX-контент с параметрами:

```tsx
<p>{intl.formatMessage(messages.greeting, { name })}</p>
```

Как надо:

```tsx
<p><FormattedMessage {...messages.greeting} values={{ name }} /></p>
```

### Исключения и границы

Строковые атрибуты, DOM API, поиск и другие потребители строк сохраняют `formatMessage`:

```tsx
<input placeholder={intl.formatMessage(messages.search)} />
<button aria-label={intl.formatMessage(messages.close)} />
<img alt={intl.formatMessage(messages.cover)} />
useEffect(() => { document.title = intl.formatMessage(messages.title); }, [intl]);
const filtered = rows.filter(row => row.name.includes(intl.formatMessage(messages.query)));
```

Тип prop важнее его имени: `title: string` требует строку, `children: ReactNode` может принимать компонент; проверь контракт. Один результат, используемый и как строка, и как JSX, нельзя целиком заменить на React element. В проекте с другим стеком сохраняют его API, например `{t('title')}` при отсутствии FormattedMessage; новое правило не служит поводом для миграции.

При исправлении сохрани descriptor/id, defaultMessage, values, locale/provider, rich text callbacks, escaping и обработку ошибок. Проверь версию: wrapper/tagName и fallback могут менять DOM и поведение. Если контекст provider, тип prop, версия API или семантика rich text неизвестны, оставь предложение. Удаляй строковый hook/импорт только после проверки всех его использований; проверяй смену локали, интерполяцию и string-only потребителей профильными тестами.

## FF-UI-001 — Оформление UI-kit через публичный API

**Область:** frontend-код, использующий UI-kit, включая CSS Modules, CSS-in-JS, global/reset и контейнеры rich text. Правило относится к потребителям библиотеки; разработка самого UI-kit определяется его собственными контрактами.

**Требование:** используй публичные props, варианты и предусмотренные настройки темы. Публичность устанавливают по документации и типам API используемой версии; наличие класса в DevTools или исходниках её не доказывает. Селекторы к внутренним классам, тегам и DOM-структуре UI-kit запрещены. Собственная внешняя обёртка для layout и отступов допустима, пока оформляет себя и не проникает внутрь компонента. Исключения FF-CSS-002 для global/reset и scoped rich text не разрешают обходить эту границу.

**Причина:** обновление внутренней разметки библиотеки должно сохранять оформление потребителей через поддерживаемый контракт.

### Парные примеры

В примерах условный @team/ui документирует Button.size, Button.variant и ThemeProvider.theme.controls.radius. Эти имена иллюстрируют контракт, а не предписывают props реальному UI-kit.

Как не надо — внутренний класс:

```css
.actions .uiButton__label { font-size: 14px; }
```

Как надо — документированный размер:

```tsx
<Button size="small">Сохранить</Button>
```

Как не надо — внутренний тег, даже внутри rich text:

```css
.richText button { border-radius: 8px; } /* button принадлежит UI-kit */
```

Как надо — предусмотренная настройка темы:

```tsx
<ThemeProvider theme={{ controls: { radius: 8 } }}><Button>Сохранить</Button></ThemeProvider>
```

Как не надо — структура без имён классов и тегов также внутренняя:

```css
.actions > * > :first-child { color: white; }
```

Как надо — публичный вариант и собственный layout:

```tsx
<div className="actions"><Button variant="primary">Сохранить</Button></div>
```

```css
.actions { display: flex; gap: 8px; margin-top: 16px; }
```

### Исключения и границы

Документированный slot API или className допустим только на предусмотренном контрактом элементе и в пределах разрешённых настроек. Сам факт наличия className не разрешает селектор `.customClass > span`. `styled(Button)` требует проверки передачи className и поддерживаемой стилизации; это не автоматическое разрешение менять внутренности. Собственные rich text теги контента остаются исключением FF-CSS-002; вложенный UI-kit — нет.

До исправления установи владельца целевого элемента, публичный контракт и влияние на все состояния. Замена внутреннего селектора публичным API допустима автоматически только при подтверждённой эквивалентности оформления и поведения. Простое удаление стиля или назначение класса внутреннему узлу не считается безопасным исправлением. При нехватке контекста сохрани код и запроси сведения; при конфликте с макетом примени FF-UI-002.

<a id="ff-ui-002"></a>
## FF-UI-002 — Явное решение по небольшому отличию макета

**Область:** небольшое отличие штатного компонента UI-kit от макета, для устранения которого потребовался бы обход публичного API. Незначительность отличия сама по себе не означает согласие ответственного за интерфейс.

**Требование:** останови требующую решения часть, сохрани спорный код и предложи разработчику принять конкретное отклонение. Укажи компонент и версию/API, маршрут и состояние, фактическое отличие от макета с доступными измерениями, штатный вариант и решение, которое нужно подтвердить. Независимые однозначные исправления можно продолжать. До явного ответа отклонение остаётся предложением; не записывай его как принятое и не объявляй задачу завершённой на этом основании.

**Причина:** выбор визуального результата принадлежит ответственному за интерфейс; проверка кода не подменяет это решение.

### Парные примеры

Как не надо: «В макете радиус 6px, у Button — 8px. Отличие небольшое, принято; задача завершена».

Как надо: «На /checkout в default-состоянии Button из @team/ui v2 имеет радиус 8px, в макете 6px. В публичном API этой версии настройки радиуса нет. Предлагаю оставить штатные 8px. Нужно решение разработчика; эта часть ожидает ответа, отклонение не принято».

Как не надо: «Чтобы совпасть с макетом, добавлен `.actions button > span { padding: 2px; }`».

Как надо: «В состоянии loading внутренний отступ Button отличается от макета на 2px; публичные size/variant не дают требуемого результата. Предлагаю сохранить штатный отступ. До решения внутренний селектор не добавляю; если точное совпадение обязательно, потребуется отдельное изменение публичного API UI-kit».

### Исключения и границы

Если макет или фактический результат недоступен, укажи недостающие данные вместо выдуманных измерений. Уже данное явное решение учитывай со ссылкой на источник и только в согласованной области; повторное согласование не нужно. Принятие визуального отклонения разрешает штатный компонент, а не вмешательство в его внутренности. Неоднозначное требование не разрешает автоматически менять дизайн или библиотеку.

Skill выдаёт запрос решения и незавершённый результат зависимой части. Надёжная остановка всей очереди существующего runner требует отдельной интеграции: установка skill её не обеспечивает. Runner и implement этим правилом не изменяются.

Раздел FF-VM относится к существующему frontend-коду с `@foxford/vm` 2.0.2. Основание: опубликованный пакет 2.0.2 (package.json: sha c678dff), [исходники этой ревизии](https://github.com/foxford/frontend-platform/tree/c678dff25f62aa53b53190e8c46263d1a4be2c9f/packages/vm), его index.d.ts и README.mdx. Контракт mapper и readonly проверен по [state/create.ts](https://github.com/foxford/frontend-platform/blob/c678dff25f62aa53b53190e8c46263d1a4be2c9f/packages/vm/src/state/create.ts), React и lifecycle — по [environment/react/index.ts](https://github.com/foxford/frontend-platform/blob/c678dff25f62aa53b53190e8c46263d1a4be2c9f/packages/vm/src/environment/react/index.ts) и [types.ts](https://github.com/foxford/frontend-platform/blob/c678dff25f62aa53b53190e8c46263d1a4be2c9f/packages/vm/src/environment/react/types.ts). README описывает назначение API, но содержит устаревшее упоминание state.destroy() в описании автоочистки; реализация 2.0.2 вызывает this.destroy(). Примеры ниже учитывают это различие.

Перед проверкой установи фактическую версию из lockfile/установленного пакета, происхождение значения и его тип. Другая версия требует сверки соответствующих типов, реализации и документации; до подтверждения совместимости сообщи неполную проверку VM и сохрани спорный код. Один import или совпадение имени map/use не доказывает контракт. Проект без VM не требует миграции; логика в hooks сама по себе не является нарушением этих правил. Обычный Array.map, другие signal-библиотеки и низкоуровневый createReactiveValue без React-расширения не получают этот контракт автоматически.

<a id="ff-vm-001"></a>
## FF-VM-001 — Стабильная ссылка mapper для .map()

**Область:** производные значения поддерживаемой VM, особенно вызовы при повторных React-рендерах.

**Требование:** повторное преобразование одного источника использует ту же mapper-функцию, пока её зависимости не изменились. Чистую функцию без захвата вынеси из рендера; зависимую от props функцию стабилизируй с полным набором зависимостей. Однократная инициализация поля VM inline-функцией допустима.

**Причина:** кеш производного состояния индексируется ссылкой mapper. Новая функция на каждом рендере создаёт новый производный store; пустые зависимости с захватом props сохраняют устаревшие значения.

### Парные примеры

Как не надо — функция создаётся на каждом рендере:

```tsx
function Total({ vm }) {
  return <span>{vm.state.count.map(n => n * 2).signal}</span>;
}
```

Как надо — чистое преобразование:

```tsx
const double = (n: number) => n * 2;
function Total({ vm }) {
  return <span>{vm.state.count.map(double).signal}</span>;
}
```

Как не надо — стабильная ссылка с устаревшим замыканием:

```tsx
const multiply = useCallback((n: number) => n * factor, []);
const total = vm.state.count.map(multiply);
```

Как надо — смена factor создаёт актуальный mapper:

```tsx
const multiply = useCallback((n: number) => n * factor, [factor]);
const total = vm.state.count.map(multiply);
```

### Исключения и проверки

`readonly doubled = this.state.count.map(n => n * 2)` при однократном создании VM допустимо: повторного рендера здесь нет. Array.map и обычный callback не относятся к правилу. Привязка `.bind()` внутри рендера также создаёт новую ссылку. Внешние изменяемые данные, прочитанные через ref или get(), не становятся зависимостью store автоматически; перенос или мемоизация не должны терять обновления. Если полный набор зависимостей или место владения неясны, оставь предложение. При исправлении проверь повторный рендер с теми же зависимостями, их смену и обновление исходного состояния. Не обещай referential equality обёрток React: кешируется базовое производное значение, расширяющий Proxy может быть новым.

<a id="ff-vm-002"></a>
## FF-VM-002 — .signal для вывода, .use() для значений

**Область:** React-расширенное состояние VM и MappedState поддерживаемой версии.

**Требование:** для непосредственного вывода реактивного значения в JSX используй `.signal`; для условий, вычислений рендера и атрибутов — значение из `.use()`. Вызывай `.use()` безусловно на верхнем уровне React-компонента или custom hook, до ранних возвратов.

**Причина:** signal — React element со своей подпиской, а use — React hook, возвращающий значение и подписывающий компонент. Элемент не является boolean или строкой для атрибута; get() не подписывает React на обновления.

### Парные примеры

Как не надо — подписка всего компонента только ради текста:

```tsx
const count = vm.state.count.use();
return <span>{count}</span>;
```

Как надо:

```tsx
return <span>{vm.state.count.signal}</span>;
```

Как не надо — React element в условии и атрибуте:

```tsx
return vm.state.visible.signal
  ? <input disabled={vm.state.busy.signal} />
  : null;
```

Как надо:

```tsx
const visible = vm.state.visible.use();
const busy = vm.state.busy.use();
return visible ? <input disabled={busy} /> : null;
```

### Исключения и проверки

Если одно значение уже нужно в условии/атрибуте или вычислении, допустимо также вывести полученное через use значение в JSX: дополнительная подписка signal не обязательна. Boolean как JSX child ничего не выводит; для текста предварительно преобразуй его стабильным mapper. Объекты требуют явного преобразования для нужного представления. Вне рендера get() допустим для моментального чтения, например в обработчике; use() в обработчике запрещён правилами hooks. signal — свойство, а не функция или тип компонента (`.signal()`, `<state.signal />` неверны). При исправлении сохрани типы props и проверь реактивные обновления текста, условных веток и атрибутов, а также порядок hooks.

<a id="ff-vm-003"></a>
## FF-VM-003 — Производное состояние readonly

**Область:** MappedState, полученный через `.map()` React-расширенного состояния VM, включая цепочки и вложенные производные поля.

**Требование:** читай производное состояние через get/use/signal/subscribe/map; запись направляй в исходное изменяемое состояние через его публичную команду. Результат map не получает set или destroy; приведение типа не разрешает запись.

**Причина:** MappedState описывает вычисляемую проекцию. В 2.0.2 set отсутствует в публичном типе, а попытка записи в mapped-значение отклоняется и на runtime.

### Парные примеры

Как не надо — попытка задать удвоенное значение:

```ts
const doubled = vm.state.count.map(double);
doubled.set(10);
```

Как надо — если контракт команды действительно задаёт исходный count:

```ts
const doubled = vm.state.count.map(double);
vm.state.count.set(5); // doubled теперь 10
```

Как не надо — запись во вложенную проекцию:

```ts
const profile = vm.state.map(selectProfile);
profile.name.set(nextName);
```

Как надо — при подтверждённом соответствии profile исходному user:

```ts
vm.state.user.name.set(nextName);
```

### Исключения и проверки

Обычная запись через немаппированное vm.state допустима. Не удаляй set без сохранения действия пользователя и не подбирай обратное преобразование наугад: фильтр, округление или агрегат часто необратимы. Для неоднозначной записи предложи команду владельца состояния и запроси её контракт. Исправление проверь вызовом пользовательского действия, изменением источника, пересчётом проекции и уведомлением подписчиков; проверь публичный тип без обхода через any/as. Освобождение принадлежит владельцу VM, см. FF-VM-004.

<a id="ff-vm-004"></a>
## FF-VM-004 — Штатное освобождение и владелец lifecycle

**Область:** жизненный цикл поддерживаемой VM, её React-владельца и общих/долгоживущих экземпляров.

**Требование:** владелец завершённого сценария освобождает VM через `vm.destroy()`. Внутренние Effector stores и state вручную вместо VM не очищают. Для отложенного освобождения владеющий компонент безусловно вызывает `vm.useAutoDestroy()` на верхнем уровне, а бизнес-логика разрешает очистку через `vm.enableAutoDestroy()` в согласованный момент завершения. enableAutoDestroy не является немедленным destroy; один useAutoDestroy без разрешения также не уничтожает VM.

**Причина:** destroy освобождает состояние и deferred-ресурсы и вызывает onDestroy. Очистка внутренностей обходит этот контракт; уничтожение общей VM отдельным дочерним потребителем ломает других владельцев.

### Парные примеры

Как не надо — подмена очистки VM внутренним Effector store:

```ts
clearNode(internalStore); // вместо завершения жизненного цикла VM
```

Как надо — в точке завершения сценария, принадлежащей владельцу:

```ts
vm.destroy();
```

Как не надо — hook в callback и ожидание немедленной очистки:

```tsx
const onFinish = () => {
  vm.useAutoDestroy();
  vm.enableAutoDestroy();
};
```

Как надо — hook у владельца; завершение сценария разрешает последующую очистку:

```tsx
function FlowRoot({ vm }) {
  vm.useAutoDestroy();
  return <button onClick={() => vm.enableAutoDestroy()}>Завершить</button>;
}
// После завершения владелец размонтируется; VM не используется повторно.
```

### Исключения и проверки

Владелец вне React может штатно вызвать destroy вручную; useAutoDestroy ему не требуется. Дочерний экран, потребляющий общую VM многошагового сценария, не становится владельцем очистки. Проверь disableAutoDestroy и сохранение VM между шагами. Не добавляй enableAutoDestroy автоматически при mount или render и не переноси уничтожение в child cleanup без доказанного владения. Сохрани пользовательские cleanup/onDestroy callbacks и отмену внешних подписок; штатный destroy не обещает отмену произвольного I/O.

Особенность реализации 2.0.2: useAutoDestroy использует effect с зависимостями `[this, this.autoDestroyEnabled]`; cleanup проверяет текущее значение флага. После enableAutoDestroy следующий рендер может запустить cleanup уже при смене зависимости, до unmount. Поэтому пример подходит для завершения с последующим уходом владельца; для продолжающегося рендера после разрешения нужна отдельная проверка поведения или явное управление lifecycle. Не обещай очистку исключительно на unmount и не исправляй эту особенность библиотеки в потребителе по догадке. Проверь фактический сценарий ререндера, размонтирование с разрешением и без него, onDestroy ровно один раз при повторном destroy и недоступность состояния после освобождения. Для StrictMode/remount и смены экземпляра VM проверь контракт проекта; автоматически подставлять уже уничтоженный экземпляр нельзя.
